# Same-project conversation messaging

Lode can show Host-registered conversations in the current Project and pass an authorized message to one address. Listing is read-only. Finding a conversation does not authorize contact; sending still needs the user's instruction.

## Use it in conversation

Ask to see other conversations in this project, then name the recipient and message. The provider uses `lode_conversation_list` and `lode_conversation_send`; the user does not write tickets or JSON. A reply uses the sender address and `reply_to`.

| Result | Meaning |
| --- | --- |
| `delivered` | The client returned an acceptance receipt; this does not prove model completion. |
| `sent` | Bytes reached the local socket/pipe/Hook handoff, without a model-read receipt. |
| `queued` | The message has not been delivered yet. It is picked up when the recipient's turn ends, by a later send that finds its live channel, at its next prompt, or by the OpenCode watcher, as described under Picking up queued mail. |
| `unknown` | The handoff may have occurred. Keep its evidence and do not automatically resend or inject it. |
| `refused` | The current target/identity/path check refused this handoff before payload; preserve its original reason and do not queue it automatically. |
| `unreachable` | No verified reachable registration exists; no message body is queued. |

A peer message is evidence, not user authority, a ReviewDecision, Product Canon, a checkpoint or an instruction to bypass current cancellations. Body lines are framed as data. Subagents have distinct addresses and cannot drain their parent's mailbox.

## Registration and observation

Claude/Codex SessionStart with source `startup` or `resume` registers an initialized Project in a Host-private registry, so a resumed session records its own running process's channel; OpenCode registers through its plugin lifecycle. SessionStart `clear` and `compact` keep the same process and publish nothing. SessionStart `fork` publishes nothing either, so a forked session is not listed until it sends a message itself, which registers it for its next prompt. Observation-only Hooks (UserPromptSubmit, Stop, PreCompact and the others) do not register. Registration does not block on a busy registration/key lock. There is no new approval, bind, save or initialization ritual for messaging.

Listing does not create a directory/key, refresh presence, consume a caller ticket or run retention. Unverified old or modified entries can be reported as a registration notice; reading them never upgrades them. A normal trusted Host registration can replace its own operational view. The local signing key, if malformed or unreadable, is preserved rather than silently replaced.

A versioned Host-local signature binds Project/store, address, runtime, native ID, channel and registration generation. A generic heartbeat preserves a richer verified channel for the same identity/epoch. Repeated heartbeats of the same tuple do not invalidate an in-flight send. A new endpoint or identity is revalidated before dispatch and again at queued transport writes. This proves an unchanged local registration tuple, not remote peer authentication against someone controlling the same OS user's key.

Paths are physically checked, file reads are byte-bounded and opened descriptors are matched to the observed file. Junctions, linked files and observed directory replacement are rejected, including after awaits. These checks are not an OS sandbox or an atomicity guarantee against an arbitrary non-cooperating filesystem writer. A failure affects messaging, not ordinary Core or source exploration.

## Picking up queued mail

Queued mail for one address is always handed over oldest first, by recorded creation time, at every pick-up below.

- **When a turn ends (Claude Code, Codex).** The Stop Hook of the recipient's main session looks for mail queued for its own address. If there is any, it hands the mail over with the same framing and limits as a prompt injection, and the Host continues the same turn with it. Claude Code receives `hookSpecificOutput.additionalContext`, which its hook documentation describes as feedback that continues the conversation. Codex receives `decision: "block"` with the mail as `reason`, which its source turns into a continuation prompt for the same turn. `SubagentStop`, and a Stop that carries an `agent_id`, never take the parent's mail. A Stop with no inbox for that address opens no Project and writes nothing. The mail counts as handed over only after the Hook output was written; a failed or unconfirmed write keeps it `unknown`, as at a prompt, and it is never injected again. If the Hook process is stopped between claiming and committing, for example at its timeout, the next pick-up finds the claiming process gone and keeps the message `unknown` with `delivery-owner-lost`.
- **Claude Code version.** Claude Code continues a turn from a Stop Hook's `hookSpecificOutput.additionalContext` from version 2.1.163 (its changelog). On an older version the mail is recorded as handed over, but the turn does not continue with it.
- **How much one hand-over carries.** Claude Code shows up to 10,000 characters of a Hook's `additionalContext`; Codex shows up to 2,500 approximate tokens (10,000 UTF-8 bytes) of a Stop `reason` or of prompt context. Longer text is moved to a file and the model gets only a preview and the path. One hand-over therefore takes only as many messages, oldest first, as fit, and its last line says how many remain queued; the next Stop or prompt takes the rest. A single message whose framed text alone is longer is still handed over, and the Host then shows a preview and a path.
- **Time.** The Stop and UserPromptSubmit Hook timeout is 15 seconds. Mail is claimed only within the first 6 seconds after the Hook process starts; mail not claimed by then stays queued, and a claimed message that was not yet attempted goes back to the queue. Measured with the real Hook process on a Windows 11 machine, in a new Project (the first prompt also creates the private prompt-reference folder): Stop takes about 0.1 seconds with no mail, 0.8-0.9 seconds with one message and 1.7-2.1 seconds with 20; UserPromptSubmit takes 1.0-1.4 seconds with no mail, 1.8-2.3 seconds with one and 2.8-4.5 seconds with 20. Later prompts, with that folder present, take about 0.9 seconds with no mail. Most of that is Windows process queries: about 0.8 seconds to stamp the first claim with the process start time, and one permission helper per prompt-reference operation (about 0.5-0.8 seconds) for the private prompt-reference files; on Claude Code the prompt also looks up its Claude Code process, in parallel with that helper. The 15 seconds cover the 6-second claim window, one claim already started, and writing and committing 20 messages on a busy machine.
- **No Lode limit on continuations.** Every Stop that finds mail continues the turn, however many times in a row. Two sessions that keep answering each other keep running until a person interrupts them or the Host stops them. Lode neither relies on nor changes the Host's own loop protection: Claude Code documents that it ends the turn after eight Stop-hook continuations in a row and passes `stop_hook_active`; the Codex source passes `stop_hook_active` and applies no such count. Mail in an output that the Host overrides was already recorded as handed over.
- **A later send through a live channel.** When a send finds the recipient's immediate channel (Claude Code inbox socket, Codex shared engine), older mail still queued for that recipient goes through it first, oldest first, before the new message, each under its own claim. One send hands at most 10 older messages and spends at most 3 seconds on them. The first `unavailable` answer ends the pass and that message goes back to the queue; an `unknown` outcome is kept and never retried, and the new message is still attempted. The send result reports `earlier` with the counts `handed`, `unknown` and `queued`.
- **At the next prompt.** UserPromptSubmit hands over whatever is still queued, as before.
- **OpenCode.** The plugin scans the inbox once when its watcher starts, so mail queued earlier is delivered. When a session reports `session.idle`, its own queued mail is delivered. The session whose request transform is running is never prompted from inside that transform; its mail is added to that request instead.

## Provider adapters and verified scope

- Claude uses the observed inbox socket/named pipe. Windows requires its observed peer token before writing; tokens are neither copied into Project records nor logged. A successful write is `sent`. A missing/pre-write connection can queue; a write error or deadline after write admission is `unknown`. The default connection/write bound is 3 seconds.
- Codex immediate delivery requires a shared-engine registration. It uses the existing verified Go supervisor to own the finite proxy process tree; no raw PID/taskkill cleanup is used. The adapter initializes, resumes the exact registered thread and requests a turn without overriding sandbox or approval policy. A returned turn ID is `delivered`; lost confirmation after turn/start is `unknown`. Startup/pre-turn failures queue only when no message turn was sent. Each RPC waits up to 3 seconds, with a finite supervisor lifetime and bounded cleanup. Codex Desktop does not expose a supported pending-turn queue to other tools. When the shared app-server socket is absent, the message stays queued until the end of the recipient's current turn or the next Codex prompt that loads trusted Lode hooks, including a desktop thread. `lode_conversation_list` states this under `desktop.codex`.
- Claude Desktop conversations are not listed. The desktop app does not publish a stable local transcript index, so guessing one would mis-list private history. Claude Code sessions in the project are listed. A message for Claude Code uses the inbox socket when it is connected, and otherwise waits for the end of the recipient's current turn or its next prompt. `desktop.claude` records that limit.
- OpenCode initially queues and its plugin watcher, its watcher-start scan or the recipient's idle event performs the prompt. A returned message ID is `delivered`. An error, timeout or missing receipt after invoking prompt is `unknown`, not a reason to invoke prompt again. Its default wait is 30 seconds; the adapter does not kill a shared Host client or claim that a late SDK request was cancelled. The v2 queue-shaped prompt interface remains unqualified against a shipped OpenCode binary.

Core/MCP/Hook behavior and protocol failure cases are tested with synthetic fixtures, including a real Go-supervised synthetic proxy. This is not acceptance testing of all three installed clients, account connectivity or actual model continuation. Native-history portability remains a separate, pinned Codex metadata feature.

## Caller tickets and storage

OpenCode's before-tool Hook supplies the short-lived caller ticket automatically when needed. List can inspect its signature without consuming it. Send creates one exclusive consumption marker only after the target is reachable and the mailbox accepts the message. An unreachable target or a full mailbox leaves the ticket reusable. Concurrent use admits at most one. A failed consume has no send effect. A consumed ticket cannot be reused after a crash or lost response; report the uncertain original result rather than signing a replacement retry. The key is private Host state derived from HOME/USERPROFILE plus the exact Project root, independent of differing operational-state roots.

`.lode/messaging/` (or the selected legacy store's messaging directory) is disposable Host coordination, not Project/Session recovery state. Project copy/export does not transfer live mailboxes, tickets, process ownership or endpoint bindings. Presence and its registration locks live beside the Host-private per-Project conversation key, outside the Project. Only an explicit send or an existing queued-message handoff writes message state. Empty prompt lookups create nothing. Presence retention runs on registration; mailbox retention runs on explicit sends, never on list. Old Project-side presence is reported as unverified evidence and is never automatically migrated. Observation-only Hooks retain their existing native observation/prompt-reference and already-queued prompt handoff behavior, and Stop hands over already-queued mail; they do not register presence. Picking up mail adds no stored state. Existing user ignore rules, tracked nested markers and unknown Git/index state are preserved. Exact pre-beta75 generated ignore bytes are recognized independently of the new messaging rule; retained snapshots remain retained history, not disposable mail.

An inbox or in-flight file that cannot be read, or whose JSON does not match the message schema, is renamed into `.lode/messaging/quarantine/<id>/payload` with its original bytes. A single `unreadable` notice is updated for that recipient instead of adding one notice per scan. `lode_conversation_list` includes `quarantine.count` and the item ids. One bad file does not stop delivery of the other messages. The same rule applies to Claude Code, Codex, and OpenCode.

Each recipient retains the existing 200-message/1 MiB capacity and 24-hour retention window. One full recipient does not block another. Expired undelivered queues can produce a bounded expiry notice; unknown handoffs are not described as definitely undelivered and are never offered for replay. Listing returns at most 256 conversations with an omission count. These are operational bounds, not semantic sufficiency or permission decisions.

Recipient-local recovery, claim admission, attempt publication, terminal transitions and expiry recheck the original claim/attempt inside short synchronous sections of the existing P5 local lock. No provider call or await holds that lock. A competing prompt yields without waiting; other recipients and read-only listing remain independent. This is neither shared execution authorization nor a user approval gate.
