# 제품 그래프

제품 그래프는 유저가 제품으로 하는 일과 그에 맞춰 시스템이 하는 일을 타입이 있는 노드와 이름 있는 연결로 적고, 둘이 만나지 않는 곳을 보여 줍니다. Lode는 원본 프로젝트 [head-agent-core](https://github.com/Won6314/head-agent-core)의 모델(`graph/build/02a-graph-definitions.md`)을 바꾸지 않고 씁니다. 13개 노드 타입, 무엇을 노드 하나로 볼지 정하는 기준, 정합성 검사, 한국어 낱말이 모두 원본 그대로입니다. 사용자가 2026-11-15에 이렇게 정했습니다. 이 문서는 Lode의 구현을 Lode의 말로 설명하며, 모델의 출처는 원본 문서입니다.

**제품 모델이 아닙니다.** 이 제품 그래프는 `context/product-model.json`에 있는 [Product Model canon](product-model.md)과 따로 있고, 그 파일을 읽지도 바꾸지도 않습니다. [Product Operating Loop](product-operating-loop.md) 문서와 `productGraph` 결과 필드는 제품 모델을 투영한 것을 "Product Graph"라고 부릅니다. 그 말은 다른 것을 가리키며 이 그래프가 아닙니다. 그 이름을 바꾸는 일은 이번 작업에 들어 있지 않습니다.

문서 쓰기, 빌드, 검사, 승인 방법은 [제품 그래프 쓰는 법](product-graph-usage.md)에 있습니다.

## 노드 타입

노드 타입 이름은 어느 언어에서나 아래에 적은 그대로 씁니다.

| 노드 타입 | 노드 하나가 무엇인가 | 어디서 나오나 |
| --- | --- | --- |
| 제품코어 | 제품이 무엇이고, 누구를 위한 것이고, 무엇을 주며, 어떻게 보이는가. 제품 하나에 하나 | 제품 정의서 |
| 유저저니 | 유저가 제품을 알게 되고, 쓰고, 떠나고, 돌아오는 단계 | 유저 저니맵 |
| IA | 화면 목록, 화면 묶음, 어디서나 갈 수 있는 메뉴 | IA 문서 |
| 유저 활동 | 유저가 한 가지 일로 받아들이는 활동과 그 차례 | 유저플로우 기획서 (활동마다 하나) |
| 화면 | 페이지 하나의 한 상태. 모달, 시트, 공통 영역도 각각 화면 | 화면설계서 (화면마다 하나) |
| 화면요소 | 화면에서 유저가 보거나, 입력하거나, 결과를 받는 것 하나 | 화면설계서의 화면요소 절 |
| 정책 | 조건 / 주체 / 행위로 쓴 규칙 하나. 종류는 처리 또는 표시 | 그래프에 직접 쓰는 한 줄 |
| 기능 | 시스템이 받아 처리하는 요청 하나 (입구 하나) | 코드, 스크립트로 |
| 코드 | 이름 붙은 코드 단위 (파일, 클래스, 함수) | 코드, 스크립트로 |
| 데이터 | 코드가 읽고 쓰는 값 중 DB가 아닌 것 | 코드: 환경 변수 읽기, 그리고 바깥 규칙이 이름 붙인 데이터 |
| 외부 연결 | 코드가 제품 밖의 서비스를 부르는 곳 | 코드. 바깥 규칙이 맞은편을 이름 붙인 곳 |
| DB | 테이블과 컬럼 | 코드: 코드 문자열이나 `.sql` 파일의 `CREATE TABLE` |
| 계측 이벤트 | 코드가 분석 도구로 보내는 이벤트 | 코드 (이 판에서는 뽑지 않음) |

화면이 없는 제품(CLI, 플러그인, 라이브러리)에서는 유저가 받는 출력 한 종류(명령 출력, tool 결과, hook이 넣는 글, 오류 메시지)가 화면이고, 그 출력 안의 한 부분이 화면요소입니다.

## 노드가 어디서 나오나

- 코드에서 나오는 노드(기능, 코드, 데이터, 외부 연결, DB)는 소스 트리와 호출 방식 표에서 스크립트로만 만듭니다. 입력이 같으면 결과도 바이트까지 같습니다.
- 문서에서 나오는 노드(제품코어, 유저저니, IA, 유저 활동, 화면, 화면요소)는 사용자가 쓴 문서에서만 나옵니다.
- 직접 쓰는 것은 두 가지입니다. 정책마다 규칙 한 줄, 기능마다 뜻 한 줄(스크립트 결과와 떨어진 따로 된 파일).
- 실행 기록(`실행 기록/`)은 프로젝트가 실행한 것과 그 출력을 Lode에 넘긴 것입니다. 노드를 만들지 않고 기능→화면요소 연결의 근거로만 씁니다(아래 실행 기록 참고). Lode는 아무것도 실행하지 않습니다.
- 그래프는 만들어지는 파일입니다. 아무도 고치지 않습니다.

## ID

| 노드 | ID 모양 | 예 |
| --- | --- | --- |
| 화면 | `<묶음 앞머리>-<번호>` | `CHT-01` |
| 화면요소 | `<화면 ID>#<번호>`, 안의 것은 하위 번호 | `CHT-01#5`, `CHT-01#3-1` |
| 유저 활동 | `UA-<묶음 앞머리>-<번호>` | `UA-CHT-01` |
| 기능 (hook, command, tool, cli) | `<종류>:<이름>` | `hook:SessionStart`, `tool:lode_project_status` |
| 기능 (프론트) | `fe/<path without extension>/<component>@<event>:<target>` | `fe/app/ui/main_window/MainWindow@clicked:_save` |
| 코드 | 파일은 `<path>`, 선언은 `<path>#<qualified name>`, 파일 안에서 이름이 겹치면 `~<n>`을 붙임 | `app/ui/main_window.py#MainWindow._save`, `app/util.py#helper~2` |
| 정책 | 정책 파일에 적은 것 | `P1` |
| 데이터 | 환경 변수는 `data:env:<NAME>`, 바깥 규칙이 이름 붙인 데이터는 `data:<이름>` | `data:env:HOME`, `data:settings` |
| 외부 연결 | `ext:<이름>`. 바깥 규칙이 붙인 이름 | `ext:billing-api` |
| DB | `db:<table>`, `db:<table>.<column>` | `db:notes`, `db:notes.title` |

## 연결

연결 이름은 양쪽 노드 타입을 `→`로 이은 것입니다. 유저 활동→화면요소, 유저 활동→유저 활동, 화면→화면요소, 화면→화면, 화면→정책, 화면→코드, 화면→기능, 화면요소→화면요소, 화면요소→기능, 기능→화면요소, 정책→기능, 기능→코드, 코드→외부 연결. 원본의 세 예외는 제 이름을 씁니다. 포함, 코드→코드의 reference 종류(call, callback, framework-invoked, render, type reference, re-render, response, enqueue, navigate, http, defines), 그리고 read / write. Lode가 더한 이름은 하나입니다. 경계, 곧 호출 방식 표에 손으로 적는 경계입니다(아래 손으로 적는 연결 참고). 다른 연결 이름은 쓰지 않습니다.

문서에서 나오는 연결은 모두 문서에 적힌 ID에서 읽습니다. 글의 뜻으로 짐작하지 않습니다.

- 차례의 단계는 화면요소 ID를 적습니다(유저 활동→화면요소). 다음 활동은 유저 활동 ID를 적습니다.
- 화면요소 줄은 조작하면 실행되는 기능(화면요소→기능)과 결과를 보여 주는 기능(기능→화면요소)을 적습니다.
- 화면 정책 절은 정책 ID를(화면→정책), 공통 영역은 다른 화면을(화면→화면), 그리는 코드는 코드 ID를(화면→코드) 적습니다.
- 화면→기능은 화면이 그리는 코드로 적은 클래스의 `@effect` 기능마다 붙습니다.
- 기능→코드는 각 기능을 그 요청을 받는 코드에 잇고, 역할은 "처리"입니다. 찾지 못하면 잇지 않습니다. 규칙의 입구는 역할이 "입구"인 기능→코드 연결을 더합니다(아래 참고). 규칙에 분기가 있는 기능은 지나는 줄 범위를 그 연결에 싣습니다.
- 빌드는 화면설계서의 줄 말고도 근거(실행 출력과 코드 문자열 리터럴)에서 찾은 기능→화면요소 연결을 더하고, 연결마다 근거를 적습니다. 이 기계 연결은 근거이지 승인이 아닙니다(아래 실행 기록 참고).

코드에서 데이터, 외부 연결, DB로 가는 연결:

- 환경 변수를 읽는 코드에서 `data:env:<NAME>`로 가는 read. 이름 붙인 데이터로 가는 read나 write와 코드→외부 연결은 바깥 규칙이 맞은편을 이름 붙인 곳에만 생깁니다.
- 표에서 그 열마다 가는 포함. SQL이 아는 표를 가리키는 코드에서 가는 read나 write.

## 저장 위치

이 파일 묶음은 Project 저장소의 `context/product-model.json` 옆에 있습니다.

```text
.lode/context/product-graph/
  제품 정의서.md
  유저 저니맵.md
  IA 문서.md
  유저플로우 기획서/UA-CHT-01.md
  화면설계서/CHT-01.md
  정책.md
  기능 뜻.md
  호출 방식 표.json
  승인/product-graph-approval-<id>.json
  확인/product-graph-check-<id>.json
  실행 기록/product-graph-run-<id>.json
  build/graph.json
  build/check.json
  build/check.txt
  build/baseline.json
  build/baseline-content.json
  build/build-context.json
```

- 문서, 정책 파일, 뜻 파일, 호출 방식 표, 승인 기록, 확인 기록(`확인/`), 실행 기록(`실행 기록/`. 둘 다 [제품 그래프 쓰는 법](product-graph-usage.md) 참고)은 `product-model.json`처럼 사용자가 가진 Canon입니다. Lode는 읽기만 하고 스스로 고쳐 쓰지 않으며, 관리 매니페스트 digest에도 들어가지 않습니다.
- `build/`는 만들어지는 출력입니다. 위 파일들과 소스 트리로 다시 만들 수 있고, Git이 무시합니다(새 Project에는 생성 저장소 규칙으로, 이미 있는 Project에는 빌드할 때마다 쓰는 자체 `.gitignore`로). `build/baseline.json`은 빌드가 비교하는 기준입니다. 첫 빌드가 잡고 `product-graph-baseline`만 옮깁니다([제품 그래프 쓰는 법](product-graph-usage.md) 참고). `build/baseline-content.json`은 `changes --list content`만 보이는 제한된 이전 본문을, `build/build-context.json`은 영향 미리보기가 비교하는 범위를 담습니다. `build/`를 지우면 기준 뒤 바뀐 것 목록과 그 전후 본문 표시만 사라집니다. Canon은 보존됩니다.
- 파일 이름은 원본의 문서 이름과 노드 ID를 씁니다. 한국어 이름을 그대로 씁니다.
- 이동용 내보내기와 가져오기는 Canon 파일을 옮깁니다(`build/`는 옮기지 않음). 이미 있는 Project로 가져올 때는 다른 Canon처럼 대상의 파일을 바꾸지 않고 보관합니다. 폴더 복사 채택은 이 파일들을 검증하고 바뀌지 않았기를 요구합니다. 세 결과 모두 `productGraph`에 다룬 문서와 승인 기록 수, 그 밖의 사용자 파일, `build/`를 옮기지 않았다는 것, Lode가 알아보지 못해 빼 둔 이름을 적고, 대상에 다른 파일이 있어 거절할 때는 그 파일을 적습니다. 실행 기록은 이 셋과 스냅숏 GC에서 확인 기록처럼 다룹니다. 실행의 출력 글은 프로젝트가 준 그대로 저장되고 이동용 내보내기에 함께 실립니다(Lode는 출력에 비밀이 있는지 보지 않습니다). `실행 기록/`이 없는 Project는 실행 근거가 없을 뿐입니다. 어느 파일도 World 입력이 아니므로, 바뀌어도 World ID는 그대로입니다.
- 스냅숏 GC는 Canon 파일을 검증된 루트로 읽고 `build/`는 건너뜁니다. 묶음 안에서 Lode가 알아보지 못하는 파일이나 폴더는 사용자의 것입니다. 지우지 않고, 루트로 쓰지 않고, issue로 치지 않으며, 남겨 둔 것으로 이름을 적습니다(`productGraphKept`). 알아보는 파일이 검증에 실패하거나 묶음 어딘가에 링크가 있으면 여전히 수거를 멈춥니다.

## 문서 형식

문서마다 원본의 고정된 절 제목을 씁니다. 칸 안의 ID가 여럿이면 쉼표로 나누고, 백틱은 있어도 없어도 됩니다. `| 항목 | 내용 |` 표에는 그 문서 자신에 대한 사실을 적습니다.

화면설계서 (`화면설계서/<화면 ID>.md`):

```markdown
# CHT-01 대화 화면

## 이 화면이 무엇인가

| 항목 | 내용 |
|---|---|
| ID | CHT-01 |
| 이름 | 대화 화면 |
| IA 묶음 | CHT |
| 공통 영역 | CMN-01 |
| 그리는 코드 | app/ui/chat.py#ChatWindow |
| 추정 | 코드만 보고 쓴 추정 |

## 개요

## 화면 흐름

## 화면요소

| ID | 한 줄 | 위치 | 조작하면 실행되는 기능 | 보여 주는 기능 |
|---|---|---|---|---|
| CHT-01#1 | 보내기 버튼 | app/ui/chat.py:40 | fe/app/ui/chat/ChatWindow@clicked:_send | |
| CHT-01#2 | 대화 목록 | app/ui/chat.py:52 | | fe/app/ui/chat/ChatWindow@effect:_poll |

## 화면 정책

| 정책 | 조건 | 주체 | 행위 |
|---|---|---|---|
| P1 | 보낼 글이 비었다 | 대화 화면 | 보내기 버튼을 막는다 |
```

```markdown
| 항목 | 내용 |

## 차례

| 차례 | 하는 일 | 화면요소 |
|---|---|---|
| 시작 | 대화 목록을 본다 | CHT-01#2 |

- UA-CHT-02
```

나머지 파일:

- 유저 저니맵: 단계와 유저 활동 열이 있는 표. 유저 활동 열에 단계마다 활동 ID를 단계 순서대로 적습니다.
- IA 문서: 화면, 이름, IA 묶음 열이 있는 표.
- 제품 정의서: 정체성, 타겟 유저, 제공 가치, 브랜딩 절.
- 정책.md: ID, 종류(처리 또는 표시), 조건, 주체, 행위, 지키는 기능 열이 있는 표.
- 기능 뜻.md: 기능과 뜻 열이 있는 표.

## 호출 방식 표

입구 하나가 기능 하나입니다. 기본 규칙이 입구를 찾고, Project는 `호출 방식 표.json`에 규칙을 더할 수 있습니다. 모든 규칙은 판단으로 표시하고, 원본처럼 처리 방식을 적습니다. 따라간다(기능을 내고 그 코드까지 따라감), 경계로 둔다(기능을 내되 따라가지 않음), 범위 밖(기능을 내지 않고 목록에만 적음).

| 종류 | 어디서 찾나 | ID |
| --- | --- | --- |
| hook | Claude Code·Codex 플러그인이나 프로젝트의 hook 설정 JSON | `hook:<event name>` |
| command | slash command 파일, 유저가 부를 수 있는 skill | `command:<name>` |
| tool | MCP tool. 프로젝트 규칙(정한 파일에 거는 패턴)으로 | `tool:<name>` |
| cli | `package.json` bin, `pyproject.toml` scripts, 프로젝트 규칙으로 찾는 하위 명령 표 | `cli:<name>` |
| 프론트 | UI 툴킷과 상관없이 UI가 유저의 신호를 코드에 잇는 곳 모두. UI 연결 패턴으로 찾음 | `fe/<path>/<component>@<event>:<target>` |

프로젝트 규칙에는 종류, 처리와 설명(없어도 됨), 그리고 tool·cli라면 파일(소스 루트 기준 경로), 패턴(첫 괄호가 이름인 정규식), 처리 코드(없어도 됨: `줄을 감싼 코드`가 기본, `파일`, 또는 표 항목이 가리키는 코드인 `항목`, Lode 추가 사항 9)를 적습니다. 종류와 처리만 적은 규칙은 기본 규칙의 처리 방식을 바꾸고, `source`에는 빼 둘 경로 앞부분을 적습니다. 어느 규칙에나 입구를, 패턴 규칙에는 분기를 더 적을 수 있습니다(둘 다 아래).

표에는 `rules` 말고도 없어도 되는 맨 위 항목이 있습니다. `"내장 이름"`(추가 사항 10), `"손으로 적는 연결"`, `"바깥"`, `"빼는 연결"`(아래)입니다. 이 항목이 없는 표는 전처럼 읽고, 모르는 항목은 여전히 거절합니다. 이 항목들의 규칙은 모두 판단으로 표시합니다.

### 입구

규칙에 `"입구": [<코드 IDs>]`를 적을 수 있습니다. 기능이 처리 코드에 앞서 거쳐 들어가는 코드로, 예를 들어 모든 tool 호출이 지나는 분배 함수입니다. 그 규칙이 내는 기능마다 역할이 "입구"인 기능→코드 연결이 붙고, 처리 코드로 가는 연결은 역할이 "처리"입니다. 종류만 있는 규칙(파일이나 패턴이 없음)에 적은 입구는 그 종류의 모든 기능에 붙습니다. 코드 노드가 아닌 ID는 규칙 문제, 규칙이 가리키는 코드가 없음입니다. Lode의 테스트가 Lode 자신의 소스에 쓰는 호출 방식 표(`test/fixtures/product-graph/lode-entry-rules.json`)는 MCP와 CLI 분배 함수를 입구로 적습니다.

닿는 길은 어디서나 두 역할 모두에서 시작합니다. 닿지 않는 코드 목록, `reach`, `changes`, `impact`, 닿는 코드 해시가 그렇습니다. 입구에서 시작한 길은 다른 기능의 처리 코드인 노드로 들어가지 않으므로(그 노드만입니다. 파일 단위 처리 코드인 파일 안의 선언에는 들어갑니다), 함께 쓰는 분배 함수 때문에 모든 기능이 모든 처리 코드에 닿지는 않습니다. 이 기능이 자기 처리 길로도 닿는 코드는 via 처리로 닿습니다. 멈춘 곳은 조용히 지나가지 않습니다. `reach <기능>`과 그 기능의 node 답은 "입구에서 다른 기능의 처리 코드 앞에서 멈춤 N곳"과 멈춘 노드·그 기능을 적고(데이터는 `entryStops`), `tree`는 그 노드와 기능을 이름으로 적으며, 한계 블록이 이 규칙을 말합니다. 이 규칙이 가릴 수 있는 것: 분배 코드가 한 기능의 처리 코드를 다른 기능들의 공통 단계로 정말 부르면 그 길은 보이지 않습니다. 기준은 입구인 연결의 역할을 함께 적어 두므로, 비교도 같은 규칙으로 이전의 닿는 범위를 다시 만듭니다.

### 분기

처리 코드가 감싼 코드(기본값)인 패턴 규칙에는 `"분기": true`를 적을 수 있습니다. 함수 하나가 여러 기능을 분기로 처리할 때 씁니다. 그러면 기능마다 그 함수의 줄에서 다른 기능의 분기 블록을 뺀 줄을 지납니다. 분기 블록은 맞은 곳을 담은 문장입니다. 중괄호 언어에서는 짝이 맞는 닫는 괄호까지, `case` 이름표는 다음 case까지, Python에서는 들여 쓴 블록 끝까지입니다. 기능→코드 연결은 그 줄 범위를 싣고, 그 처리 코드에서 시작한 닿는 길은 그 줄의 참조만 따라갑니다(더 깊은 코드는 통째로 닿습니다). 그런 처리 코드의 참조는 나오는 줄을 모두 적습니다. 블록을 정하지 못한 곳은 함수 전체를 지나고 분기를 정하지 못함에 나옵니다. 분기를 적지 않으면 아무것도 바뀌지 않습니다.

### 손으로 적는 연결

스캔이 보지 못하는 연결은 사람이 판단 규칙으로 적을 수 있습니다. `{"판단": true, "종류": "framework-invoked" | "경계", "파일", "글", "대상": [<코드 IDs>], "설명"}`입니다.

- framework-invoked: 파일에서 글이 있는 코드 줄마다 그 줄을 감싼 코드에서 대상마다 가는 참조가 생기고, 판단으로 표시됩니다(`judgement: true`, 글 "(판단)"). 닿는 길이 이것을 따라갑니다.
- 경계: 경계 연결입니다. 닿는 길은 이것을 넘지 않습니다. 질의는 멈춘 노드 아래에 "경계에서 멈춤: <설명> → <대상>"을 내고, 경계 뒤에 있는 코드의 `reach <code>`는 "경계를 넘으면 닿는 기능 N개 (…)"를 말합니다.

글이 어느 코드 줄에도 없거나, 파일이 없거나, 대상이 코드 노드가 아니면 규칙 문제 "규칙이 낡음 — …"로 목록에 나오고, 빌드는 실패하지 않습니다.

### 바깥 (바깥 호출에 이름 붙이기)

바깥 모듈 표에서 들여온 이름으로 부른 호출은 사실로 적습니다. JavaScript `fs`, `fs/promises`, `net`, `http`, `https`, `dgram`, `tls`, `child_process`, `readline`, Python 내장 `open`, `os`, `shutil`, `pathlib`, `subprocess`, `socket`, `sqlite3`, `urllib`, `http.client`, 그리고 바깥 규칙이 적은 모듈입니다. 사실은 판단 규칙이 있을 때만 연결이 됩니다. `"바깥": [{"판단": true, "이름", "종류": "데이터" | "외부 연결", "닿는 곳": [{"모듈", "파일"?, "줄"?, "선언"?}], "설명"?}]`입니다.

- 데이터: 노드 `data:<이름>`과, 부른 api 이름에 따른 read 또는 write. 어느 목록에도 없는 api는 짐작하지 않고 읽기·쓰기를 정하지 못함에 나옵니다.
- 외부 연결: 노드 `ext:<이름>`과 코드→외부 연결.
- 어느 규칙도 맡지 않은 사실은 모듈·파일별로 이름 없는 바깥 호출에 나옵니다. 두 규칙이 맡은 사실은 규칙 문제입니다. 그중 정확히 하나만 줄이나 선언으로 좁혔으면 그 규칙이 맡습니다.

### UI 연결 패턴 (프론트)

프론트 기능은 UI를 거친 유저의 신호입니다. 클릭, 키, 컨트롤 값 바꾸기, 화면 열기와 닫기가 그렇습니다. 툴킷은 그 연결을 코드에 어떻게 쓰는지만 정하므로, 툴킷은 데이터입니다. 방식 하나가 모든 UI 연결 패턴을 읽고, 어느 툴킷에도 따로 된 코드가 없습니다. 패턴은 표의 프론트 항목이며 다음을 적습니다.

- 이름과 확장자(어떤 파일), 그리고 필요하면 파일 표시(파일에 있어야 하는 정규식).
- 모양: 이름 붙은 괄호 `event`, `target`, 필요하면 `emitter`가 있는 정규식. 또는 메서드: 클래스 안에 선언된 메서드 이름에 거는 정규식(다시 정의한 이벤트 메서드).
- 코드만(맞은 곳이 코드에서 시작해야 함), 대상 읽기(식: 대상이 식 끝까지 이어짐), 이벤트 고정과 이벤트 바꾸기(이벤트 이름을 어떻게 쓰는가).
- 요소 이름: 대상이 핸들러 이름이 아닐 때 요소 이름을 어디서 가져오는가(신호를 보내는 객체, 같은 태그의 id, 같은 줄에서 대입한 이름).
- 유저 조작(유저의 조작인 이벤트. 모든 이벤트면 `*`, 예외는 유저 조작 아님)과 스스로 도는(화면이 스스로 도는 이벤트).

Lode의 기본 패턴도 같은 표, 같은 형식의 항목이고, 프로젝트 항목과 같은 검사를 거칩니다. 이름이 같은 프로젝트 항목은 기본 항목을 바꾸고, 새 툴킷은 항목을 써서 더하며 Lode를 고칠 필요가 없습니다.

| 갈래 | 기본 표 항목 (모두 같은 표의 항목 하나씩) | 잇는 모양 예 |
| --- | --- | --- |
| DOM | `DOM addEventListener`, `DOM on<event> 속성`, `DOM 타이머`, `HTML on<event> 속성` | `button.addEventListener("click", save)` |
| 구성요소 템플릿 | `JSX on<Event>`, `React useEffect`, `Vue @event / v-on:`, `Vue onMounted`, `Svelte on:event`, `Svelte onMount` | `onClick={save}` |
| signal/slot·callback 툴킷 | `Qt signal.connect`, `Qt <name>Event 메서드`, `Tk command=`, `Tk bind`, `Tk after` | `button.clicked.connect(self.save)` |

항목의 유저 조작 목록에 있는 이벤트만 기능이 됩니다. 모양은 맞지만 유저의 조작이 아닌 연결(내부 알림, 사용자 정의 signal, 애니메이션 끝 이벤트)은 핸들러를 찾으면 코드→코드 callback으로 적고, 기능으로 삼지 않은 연결 목록에 넣습니다. UI 코드처럼 보이는데(표의 화면 코드 표시, 또는 화면 파일에 적힌 파일) 어느 패턴에서도 연결이 나오지 않는 파일은 화면 코드인데 규칙이 없음 목록에 넣습니다. 그래서 빠진 패턴은 기능 0개가 아니라 빈 곳으로 드러납니다.

## 정합성 검사

검사 하나가 원본의 여섯 줄을 문구와 뜻 그대로 냅니다.

| 그래프에서 보이는 것 | 뜻 |
| --- | --- |
| 제품코어와 부딪히는 정책 | 정책이나 제품코어 중 하나가 틀렸다 |
| 화면요소 → 기능이 있는데 그 화면요소를 가리키는 유저 활동이 없다 | 기획에 빠진 일이거나 쓰이지 않는 기능 |
| 앞 활동의 화면에서 다음 활동의 화면으로 가는 navigate가 없다 | 막힌 동선 |
| 어떤 유저 활동도 가리키지 않는 화면 | 목적 없는 화면 |
| 화면 정책 절과 정책 노드가 다르다 | 둘 중 하나가 낡았다 |
| 유저 활동의 다음 활동과 유저저니 순서가 다르다 | 둘 중 하나가 낡았다 |

줄마다 정확히 하나로 끝납니다. 노드 ID와 위치가 붙은 발견 목록, 0건, 또는 이유가 붙은 검사 못 함. 0건은 적어도 한 번 비교했을 때만 냅니다.

- 제품코어와 정책은 기계로 정하지 않습니다. 사람이 읽도록 둘을 나란히 냅니다.
- 이 판은 navigate를 뽑지 않으므로, 그 줄은 늘 왜 하지 못했는지 적습니다.
- 화면 정책 줄은 정책 ID마다 화면설계서에 적은 조건, 주체, 행위를 정책 줄과 비교하고, 화면 정책으로 적힌 처리 정책도 짚습니다.
- 유저저니 줄에는 단계마다 활동 ID를 적은 유저 저니맵이 필요합니다. 다음 활동이 앞 단계에 있거나 저니에 없는 활동이면 짚습니다.

그 밖에 개수와 함께 목록을 냅니다. 문서가 가리키는데 없는 ID, 어떤 화면요소·화면도 가리키지 않는 기능, 어느 기능에서도 닿지 않는 코드, 이유별로 센 하나로 정하지 못한 호출, 코드로 읽지 않은 파일, 기능이 없어진 뜻 줄(사라진 기능의 뜻), 이유가 붙은 처리 코드를 찾지 못한 기능, 기능으로 삼지 않은 연결, UI 코드처럼 보이는데 맞는 패턴이 없는 파일(화면 코드인데 규칙이 없음), 경로로 파일을 실행한다고 읽은 모든 곳(경로로 실행으로 읽은 곳. 여러 파일에 맞는 경로는 경로가 여러 파일에 맞음으로 셈), 규칙 문제(규칙이 가리키는 코드가 없음, 규칙이 낡음 — …), 분기를 정하지 못한 기능(분기를 정하지 못함), 바깥 규칙이 이름 붙이지 않은 바깥 호출(이름 없는 바깥 호출)과 읽는지 쓰는지 알 수 없는 이름 붙인 데이터(읽기·쓰기를 정하지 못함), 실행과 근거 목록(아래 실행 기록 참고), 노드 타입별 개수(데이터, 외부 연결, DB는 그 수가 무엇을 세는지와 함께. 뽑지 않음은 계측 이벤트에만), 문서별 상태. 이 모든 것 앞에 이 그래프가 답하지 못하는 것 블록 하나가 먼저 나옵니다(Lode 추가 사항 6).

## 승인

사용자가 승인한 문서만 제품 설명으로 셉니다. 문서(또는 정책 파일)는 지금 본문 digest에 대한 승인 기록이 있을 때만 승인입니다. 고치면 다시 승인받을 때까지 추정으로 돌아가고, 검사는 이를 한 번도 승인되지 않은 문서와 나눠 승인 뒤 바뀜으로 보여 줍니다.

승인 digest는 파일의 바이트가 아니라 본문으로 계산합니다. 사용자가 승인한 것은 문서가 말하는 내용이기 때문입니다. 바이트를 UTF-8로 읽고, 맨 앞 BOM 하나를 떼고, CRLF와 홀로 있는 CR을 모두 LF로 바꾸고, NFC로 정규화한 뒤, 그 결과의 UTF-8 바이트로 SHA-256을 냅니다. 그 밖에는 아무것도 정규화하지 않습니다. 줄 끝 공백, 마지막 줄바꿈, 빈 줄, 보이는 글자는 모두 digest를 바꿉니다. 승인 기록은 이 기준을 `digestBasis`에 적습니다. 다른 digest(만들어지는 파일, 내보내기·가져오기 무결성, GC 목록)는 그대로 바이트 digest입니다. 문서 안에 적은 상태 낱말은 아무것도 증명하지 않습니다. 승인되지 않은 문서는 어느 쪽 추정인지 `| 항목 | 내용 |` 표에 추정: 코드만 보고 쓴 추정 또는 화면만 보고 쓴 추정으로 적습니다. 기본 검사는 승인된 문서만 쓰고, 추정 옵션을 주면 추정 문서도 쓰되 그것에 기댄 발견마다 표시를 붙입니다.

## 코드 층과 그 정밀도

코드 층은 Lode의 정규식 기반 소스 분석(저장소 World Model과 같은 스캔)을 다시 씁니다. 파일과 선언마다 노드 하나이고 줄 범위와 종류가 붙습니다. 구문 트리가 아니므로 다음과 같습니다.

- 코드→코드 call은 부르는 이름이 선언이나 불리는 값 바인딩 하나로 정해질 때만 적습니다(같은 파일, 감싼 클래스의 `self.` 또는 `this.` 메서드, 찾은 모듈에서 들여온 이름, 그리고 추가 사항 10의 글자 규칙). 나머지 호출은 정하지 못한 호출로 셉니다.
- reference 종류는 call, callback, framework-invoked 셋을 적습니다. 스캔이 구별하지 못하는 종류(render, type reference, re-render, response, enqueue, navigate, http, defines)는 적지 않습니다.
- callback은 기능으로 삼지 않은 UI 연결과, 값으로 쓴 함수에 적습니다. 값으로 쓴 함수는 부르지도, 선언하지도, 들여오지도, export 목록에 적지도 않았고, 속성 이름이나 점 뒤가 아닌 이름으로, 호출과 같은 규칙으로 함수나 클래스 선언 하나로 풀리는 것입니다. 멤버는 호출이 풀리는 곳에서만 풉니다. 클래스 안의 `this.x`나 `self.x`, 제품 클래스의 static `C.x`, 모듈 수준 객체 리터럴이나 namespace import의 `name.x`입니다. 줄인 속성(`{ run }`)도 셉니다. 매개변수와 지역 변수는 풀지 않습니다. TypeScript의 타입 자리(`:`나 `satisfies` 뒤), `<…>` 안의 글, 데코레이터, `const { … } = require(…)`는 쓰임이 아닙니다. 한계 블록은 "값으로 쓴 함수 N곳(이름 a, 멤버 b)"을 호출과 따로 셉니다.
- framework-invoked는 두 모양만 적습니다. 첫째, 코드의 문자열이나 템플릿 리터럴이 스캔한 코드 파일 정확히 하나의 경로(전체 상대 경로, 또는 `/`에서 시작하는 그 뒷부분)로 끝나고, 그 글자를 실행하거나 적재하는 호출에 넘길 때만입니다. 동적 import, 프로세스 시작(`spawn`, `spawnSync`, `fork`, `exec`, `execFile`과 그 sync 형태, Python `subprocess.run`, `Popen`, `call`, `check_call`, `check_output`, `os.system`, `exec` 계열, `runpy`), `Worker`, 또는 `process.execPath`나 `sys.executable`도 함께 넘기는 호출입니다. 경로를 만드는 함수(`join`, `resolve`, `URL` 같은 것), 배열, 객체는 건너 봅니다. 공백이 있는 글자는 명령 줄입니다. 그 경로는 프로그램 자체이거나, 언어의 실행기(`node`, `python` 같은 것. 플래그는 건너뜀) 뒤의 스크립트일 때만 셉니다. 그래서 `"git add src/x.js"`는 아무것도 잇지 않습니다. 둘째, 바인딩 없는 JavaScript·TypeScript `import "<relative path>"`입니다. 두 파일에 맞는 경로는 연결을 만들지 않고 셉니다(경로가 여러 파일에 맞음). import, export, require의 경로는 이렇게 읽지 않고, 파일은 자기 자신을 가리키지 않습니다. 상수에 담았다가 뒤에서 넘기는 경로, 주입, 데코레이터, 파일 이름으로 정하는 경로는 보지 못합니다. 읽은 곳은 모두 경로로 실행으로 읽은 곳에 나오므로 틀린 곳을 알릴 수 있습니다. (예전 규칙은 파일 이름을 가리키는 리터럴을 모두 받았는데, Lode 자신의 코드에서 연결 30개를 뽑아 보니 15개가 언급일 뿐이어서, 실행하거나 적재하는 리터럴로 좁혔습니다.)
- JavaScript 클래스 메서드는 선언입니다(추가 사항 10). 그래도 그 안의 UI 연결은 감싼 클래스를 구성요소로 쓰고, 객체 리터럴 멤버 안의 연결은 감싼 함수나 파일 이름을 씁니다. 그래서 프론트 ID는 그대로입니다.
- UI 연결은 패턴의 정규식으로만 찾습니다. 여러 줄에 걸친 연결, 문자열로 만든 연결, 툴킷이 이름으로 자동으로 잇는 연결, 실행 중에 이벤트 이름을 계산하는 연결은 보지 못합니다. 코드만으로 표시한 항목은 글자 단위 lexer가 코드인지 가립니다. JavaScript, TypeScript, Python 파일에서는 주석이나 문자열(여러 줄 문자열과 템플릿 문자열 포함) 안에서 맞은 것을 버리고, HTML, Vue, Svelte 파일에서는 `<!-- -->` 주석만 버립니다. JSX `on<Event>={…}` 속성은 가리지 않습니다. lexer는 파서가 아니어서 정규식 리터럴을 바로 앞 글자로만 알아봅니다. 같은 태그의 id는 가장 가까운 `<`와 `>` 사이에서 찾으므로 속성 안의 `>`에 흔들릴 수 있습니다. 다시 정의한 이벤트 메서드는 이름으로만 알아보고, 그 클래스가 정말 UI 클래스를 상속하는지는 보지 않습니다.
- HTML, Vue, Svelte 파일의 핸들러는 코드에 잇지 않습니다. 그 파일들은 소스 분석에 들어가지 않기 때문이며, 그 기능은 처리 코드를 찾지 못한 기능 목록에 나옵니다.
- 데이터는 환경 변수를 `process.env.NAME`, `process.env["NAME"]`, `os.environ["NAME"]`, `os.environ.get("NAME")`, `os.getenv("NAME")`으로 읽을 때만 읽고, 그때마다 `data:env:NAME`과 read 연결을 냅니다. 그 변수에 대입하거나 `delete`하면 write 연결입니다. `const { NAME } = process.env`는 꺼내는 이름마다 읽음입니다. 환경 객체를 다른 이름에 담아 넘기면 따라가지 않습니다. 그 밖의 데이터와 모든 외부 연결은 바깥 규칙에서만 나옵니다. 호출만 보고 짐작하지 않습니다.
- DB는 코드 문자열이나 `.sql` 파일의 `CREATE TABLE`에서 읽습니다. `db:<table>`과 `db:<table>.<column>`, 그리고 포함입니다. 표는 그 동사의 자리에 있을 때만 셉니다. 표마다 따로 정합니다: `FROM <t>`나 `JOIN <t>`는 읽기, `INSERT INTO <t>`, `REPLACE INTO <t>`, `UPDATE <t> … SET`, `DELETE FROM <t>`는 쓰기입니다(`INSERT INTO a SELECT … FROM b`는 a를 쓰고 b를 읽습니다). 코드 문자열은 동사가 제자리에서 이름을 받을 때만 SQL로 읽은 곳입니다. 그런 문자열은 모두 SQL로 읽은 곳에 적고, 이름마다 읽기, 쓰기, 또는 `CREATE TABLE`이 만들지 않았으면 표를 모름으로 적습니다(표가 어딘가 있지만 읽지 못한 것이라 드러낼 만한 빈곳입니다). 영어 문장처럼 동사 낱말만 있는 문자열은 SQL로 읽은 곳이 아닙니다. 다른 방법으로 만든 표는 보지 못합니다. 표와 데이터에는 뜻 줄이 없습니다.
- 노드 개수는 데이터, 외부 연결, DB를 수로, 각각 무엇을 세는지와 함께 냅니다. 계측 이벤트, navigate, C4 묶음은 뽑지 않습니다. 출력은 0 대신 뽑지 않음이라고 적습니다.

### 어느 기능에서도 닿지 않는 코드

원본의 코드 정의는 어느 기능을 처리하는 코드에서 reference를 따라가도 닿지 않는 코드를 목록으로 만들라고 합니다. Lode는 이를 어느 기능에서도 닿지 않는 코드로 냅니다.

- 모든 기능의 찾은 처리 코드와 입구 코드에서 시작해, 풀린 call, callback, framework-invoked reference(판단으로 적은 것 포함)를 끝까지 따라갑니다. 경계는 넘지 않고, 입구에서는 다른 기능의 처리 코드로 들어가지 않습니다. 분기가 있는 처리 코드에서는 그 기능의 줄에 있는 참조만 따라갑니다.
- 처리 코드가 파일 전체인 경우(hook 스크립트, command 파일, bin 스크립트) 그 파일과 파일 맨 위에서 하는 호출까지 닿은 것으로 봅니다. 그 파일 안의 선언은 풀린 reference로만 닿습니다. 클래스에 닿으면 그 생성자(`__init__` 또는 `constructor`)에 닿은 것으로 봅니다.
- 들르지 않은 선언을 모두 적습니다. 아무것도 닿지 않는 파일과, 다른 곳은 닿는 파일 안의 닿지 않는 선언을 나눠 적습니다.
- 이 목록은 reference만큼만 믿을 수 있습니다. 머리 줄에 전체 호출 중 풀린 호출 수를 적고, 닿지 않음은 풀린 경로를 찾지 못했다는 뜻이지 죽은 코드라는 뜻이 아님을 적습니다. 빠진 기능인지 죽은 코드인지는 읽는 사람이 판단하고, 스크립트는 찾지 않은 이유를 붙이지 않습니다.

## 실행 기록과 기능→화면요소의 근거

Lode는 아무것도 실행하지 않습니다. 프로젝트가 실행한 것을 Lode에 넘길 수 있고(`product-graph-runs-add`, [제품 그래프 쓰는 법](product-graph-usage.md) 참고), 실행마다 그때 빌드의 기능 내용·닿는 코드 해시와 코드를 읽은 방식이 함께 저장됩니다. 그래서 옛 코드에서 한 실행이 오늘 코드의 근거가 되는 일은 없습니다. 실행은 `R<record short id>-<n>`으로 보입니다.

빌드는 화면설계서의 줄 옆에 근거로 기능→화면요소 연결을 매번 새로 만듭니다.

- **따옴표로 묶은 글.** 화면요소 줄의 글은 그 한 줄 칸에서 백틱으로 묶은 조각 중 글자 그대로인 글자가 4자 이상인 것입니다. 그 안의 `<…>`와 `…`는 어떤 글에도 맞습니다. 글자 그대로인 글자가 10자 이상인 글이 있는 줄은 더 짧은 글을 쓰지 않습니다.
- **실행 근거.** 지금도 맞는 실행의 출력에 그 글이 있으면 그 실행의 기능에서 연결이 생기고, 근거는 "실행 <ids>"입니다.
- **코드 근거.** 어느 실행에도 맞지 않은 요소, 또는 줄에 보여 주는 기능을 적은 요소(그때 문서는 기능을 좁힐 뿐 넓히지 않습니다)는 그 글이 코드 문자열 리터럴에 있거나 그 글을 담은 모듈 수준 상수가 쓰인 곳에 있으면, 그 코드에 닿는 기능에서 연결이 생기고 근거는 "코드 <file>:<line>"입니다. 풀리지 않은 상수 쓰임은 목록에 나옵니다.
- 줄에 적은 보여 주는 기능은 근거 "문서"를 그대로 갖습니다. 연결 하나는 가진 근거를 종류마다 모두 적습니다.
- 호출 방식 표의 판단 규칙 `"빼는 연결": [{"판단": true, "기능", "화면요소", "이유"}]`은 틀린 기계 연결을 뺍니다(문서 자신의 연결은 남습니다). 어느 기계 연결에도 맞지 않는 규칙은 규칙 문제, 규칙이 낡음입니다.

기계 연결은 문서의 상태(승인 또는 추정)를 따르고, 근거이지 승인이 아니며, 문서·승인·확인 기록을 바꾸지 않고, 어느 다시 볼 것 목록에도 들지 않으며, 빌드마다 다시 만들어집니다. 검사는 문서에만 있음(실행·코드 근거 없음), 실행·코드에만 있음(문서에 없음), 이유가 붙은 이어지지 않은 화면요소, 풀리지 않은 상수 쓰임, 규칙으로 뺀 기계 연결을 적습니다.

기록한 뒤 기능이 바뀐(내용, 닿는 코드, 코드를 읽는 방식) 실행은 연결을 만들지 않고 실행 뒤 코드가 바뀜으로 나옵니다. 같은 기능·같은 실행 이름의 새 실행은 옛 실행을 대신합니다. 한계 블록은 Lode가 아무것도 실행하지 않았다는 것과 어떤 실행 기록을 읽었는지 말합니다.

## 읽는 방식 2판

입구, framework-invoked, 값으로 쓴 함수, 데이터·외부 연결·DB, 분기 읽기는 코드를 읽는 방식을 바꿉니다(`PRODUCT_GRAPH_VERSION` 1 → 2). 그래서 업데이트 뒤 첫 빌드는 옛 방식으로 읽은 기준과 비교합니다. 그 빌드는 읽는 방식 때문에 달라진 것을 실제 변경과 나눠 보여 줍니다. 무엇을 보여 주는지와 새 기준을 잡는 법은 [제품 그래프 쓰는 법](product-graph-usage.md)에 있습니다.

## 사용자가 2026-11-15에 승인한 Lode 추가 사항

원본에 없는 것으로, 사용자가 승인한 추가 사항입니다.

1. **어느 UI 툴킷에서나 쓰는 프론트 ID.** 원본은 프론트 규칙을 React를 예로 들어 적습니다. Lode는 같은 규칙을 어느 UI 툴킷에나 씁니다. `<component>`는 감싼 구성요소, 클래스나 함수이고, 파일 단위 연결이면 그 파일 이름입니다. `<event>`는 툴킷이 쓰는 그대로의 이벤트나 signal 이름이고(`onClick`이면 `click`, `clicked`, `Button-1`), 다시 정의한 이벤트 메서드면 메서드 이름에서 `Event`를 뗀 것(`close`)입니다. `<target>`은 핸들러 이름, 없으면 요소의 id나 신호를 보내는 객체 이름, 둘 다 없으면 `요소#순번`입니다. 화면이 스스로 도는 것(`useEffect`, `DOMContentLoaded`, 타이머)은 `@effect:<name>`입니다. 위의 기본 패턴 표는 이 규칙 하나를 툴킷별 예로 보여 줍니다.
2. **기계 상대.** 기계 상대(다른 서비스, 컨트롤러, 장치)는 유저가 아니라 외부 연결입니다.
3. **실행하지 않은 제품의 근거.** 근거는 코드 위치(파일과 줄)뿐이고, 문서는 코드만 보고 쓴 추정으로 표시하며, 실행 근거를 지어내지 않습니다. 실행 근거는 프로젝트가 넘긴 실행 기록에서만 나옵니다.
4. **유저 활동 ID.** `UA-<묶음 앞머리>-<번호>`.
5. **Skill.** 유저가 부를 수 있는 skill은 command로 셉니다.
6. **이 그래프가 답하지 못하는 것.** 빌드와 검사의 글은 고정된 블록 하나로 시작하고, 구조화된 결과와 만들어지는 파일에도 같은 객체(`limits`)가 들어갑니다. 코드를 어떻게 읽었는지(정규식 스캔, 구문 트리 아님, 타입 없음), 세 수로 나눈 호출(추가 사항 10), 적는 reference 종류(call, callback, framework-invoked)와 구별하지 못하는 종류, framework-invoked를 어떤 모양에서 읽는지, 값으로 쓴 함수(호출과 따로 셈), 데이터·외부 연결·DB를 무엇에서 읽는지와 그 수, 뽑지 않은 노드 타입과 연결, UI 연결 스캔의 한계, 아무것도 실행하지 않았다는 것(실행 기록이 있으면 몇 개를 읽었고 몇 개가 아직 맞는지), 승인과 추정 문서 수와 이번 실행이 쓴 문서. 이 사실들은 글의 다른 곳에서 되풀이하지 않습니다.
7. **이유별로 센 못 푼 호출.** 하나로 정하지 못한 호출은 스캔이 정한 이유 하나에만 셉니다. 같은 이름의 선언이 여럿, 호출처럼 보이는 언어 키워드, 스캔한 코드 어디에도 없는 선언, 제품 밖에서 들여온 이름, 타입을 모르는 받는 쪽(호출한 줄에서 읽은, 식에 붙은 메서드 호출 포함), 다른 파일에만 있고 잇는 import가 없는 선언, 그리고 나머지를 위한 명시된 그 밖. 이유들의 합은 전체와 같고, 이유마다 무엇이 있으면 정해지는지 한 줄씩 적습니다. 소스 루트 아래에서 코드로 읽지 않은 파일은 읽고도 못 푼 코드와 나눠 확장자별로 보지 않음으로 셉니다. 처리 코드를 찾지 못한 기능은 그 이유를 적습니다.
8. **정체성과 보존.** 노드 ID는 이름 구조이고 줄 번호를 담지 않습니다. 파일, 줄 범위, digest는 속성입니다. 파일 안에서 종류와 상관없이 qualified name이 겹치는 선언은 `~<n>`, 곧 그 파일 안 같은 이름 선언 중 몇 번째인지를 붙입니다. 같은 이름의 선언이 그 앞에 생기거나 없어지거나 순서가 바뀔 때만 바뀌고, 두 번째가 생기면 첫 번째에 `~1`이 붙습니다. 프론트 ID의 `요소#순번`은 원본의 기본값이라 그대로 둡니다. 빌드는 `기능 뜻.md`와 `정책.md`를 고쳐 쓰거나 순서를 바꾸거나 줄을 지우지 않습니다. 이름이 바뀐 기능은 새 ID가 됩니다. 옛 뜻 줄은 적힌 그대로 남아 사라진 기능의 뜻에 나오므로 사람이 옮겨 붙일 수 있고, 옛 ID를 가리키는 정책 줄은 문서가 가리키는데 없는 ID에 나옵니다.
9. **표 항목의 처리 코드.** 많은 제품이 입구를 표의 항목으로 등록합니다. 객체 배열, 이름 → 핸들러 맵, 등록 호출의 사슬이 그렇습니다. `"처리 코드": "항목"`을 적은 tool·cli 규칙은 기능의 처리 코드를 그 항목에서 가져옵니다. 항목은 코드 마스크로 찾습니다. 맞은 곳을 담은 가장 바깥 리스트·객체·딕셔너리 리터럴의 직접 원소(함수, 클래스, 블록 본문을 넘지 않음)이고, 그런 리터럴이 없으면 맞은 곳을 담은 문장(`.`로 시작하는 호출 사슬 줄 포함)이며, 가장 안쪽 함수, 클래스, 블록 본문 밖으로 나가지 않습니다(콜백 하나 안의 등록 호출 둘은 항목 둘). 맞은 곳의 줄이 데코레이터 줄이면(줄이 `@`로 시작하면, 패턴이 `@`로 시작하든 그 뒤에서 시작하든) 빈 줄과 다른 데코레이터를 건너뛴 뒤 그것이 꾸미는 정의입니다. JavaScript·TypeScript 데코레이터는 꾸미는 정의를 스캔이 선언으로 가질 때만 셉니다(클래스 메서드는 선언입니다). 문장 항목에서는 그 문장 자신의 호출 사슬(등록하는 호출, 예를 들어 `registry.register(…)`나 `program.command(…).action(…)`)을 처리 코드로 읽지 않습니다. 제품 코드여도 그렇고, 그 인자는 읽습니다. 항목은 함수 본문처럼 읽습니다. 선언 하나로 풀리는 이름(값으로 쓴 함수, 항목 안 함수의 호출), import를 거친 `namespace.member`, 그리고 경로를 글자로 쓴 동적 import에서 같은 식으로 꺼낸 이름(`import("./x.mjs").then((m) => m.run)`, `.then(({ run }) => …)`, `(await import("./x.mjs")).run`, `const { run } = await import("./x.mjs")`)입니다. 이 동적 import 모양은 호출을 읽는 곳 어디서나 호출로 읽고, 경로가 글자가 아니거나 꺼내는 이름이 없는 동적 import는 따로 된 못 푼 이유로 셉니다. Python 동적 import(`importlib`)는 읽지 않습니다. 아무것도 풀리지 않은 항목의 기능은 이유와 함께 처리 코드를 찾지 못한 기능에 나옵니다. 일부 이름은 풀렸지만 동적 import가 풀리지 않은 항목은 풀린 처리 코드를 그대로 쓰고, 동적 import 이유와 함께 일부만 풀린 기능으로도 나옵니다. 알려진 약점: 한 항목에서 나온 기능 둘은 그 항목의 처리 코드를 함께 씁니다. 여러 항목에서 나온 기능은 모든 항목의 처리 코드를 갖고 위치와 함께 목록에 나오므로, 언급까지 맞는 패턴이 드러납니다.
10. **호출 정밀도.** 스캔은 호출이 무엇인지 말하고, 타입 없이 풀 수 있는 호출을 풉니다.
    - **어떤 모양이든 import 목록.** 여러 줄에 걸친 import 목록, 끝 쉼표나 안의 주석이 있는 목록은 같은 목록을 한 줄에 쓴 것과 같은 바인딩을 냅니다. default import와 namespace import를 함께 쓴 것도 그렇습니다. Python에서 괄호로 감싸 여러 줄에 쓴 목록과 역슬래시로 이은 줄도 한 줄과 같게 읽습니다.
    - **멤버는 선언입니다.** JavaScript·TypeScript 클래스 본문의 메서드(보통, async, static, 제너레이터, getter, setter, private)와 함수를 담은 클래스 필드는 한정 이름 `<Class>.<method>`인 선언이고, Python 메서드가 이미 그랬던 것과 같습니다. 이름에 묶은 클래스 식(`const A = class {`)은 그 이름의 클래스이고, 이름 없는 default 클래스는 클래스 `default`입니다. 모듈 수준 이름에 묶인 객체 리터럴의 함수 멤버(`const api = { run() {…}, stop: () => {…} }`)는 한정 이름 `<binding>.<member>`인 선언입니다. 중첩된 객체 리터럴, 모듈 수준 이름에 묶이지 않은 리터럴, 따옴표나 계산한 이름(`[Symbol.iterator]() {`)은 선언이 아닙니다. 메서드를 정의하는 자리(`name(…) {`)와 본문 없는 TypeScript 시그니처(`abstract render(): void;`, 오버로드, interface 멤버)는 호출로 세지 않습니다.
    - **글자로 정하는 받는 쪽.** 메서드나 클래스 필드 안의 `this.x(`(Python `self.x(`)는 그 클래스의 멤버로 풉니다. 클래스에 그 이름이 없지만 다른 클래스를 상속하거나 그 이름을 본문 없는 시그니처로만 가지면 상속받은 멤버일 수 있는 호출로 셉니다(상속은 따라가지 않습니다). `C.x(`는 제품 클래스의 static 메서드로 풉니다(Python은 어떤 메서드든). `name.x(`는 그 이름에 묶인 객체 리터럴의 멤버로, 같은 파일이나 import를 거쳐 풉니다. `v.x(`는 `v`가 같은 함수나 모듈 수준에서 `const v = new C(…)`(Python `v = C(…)`, 한 번만 대입)로 한 번 만들어졌을 때 풉니다. 다시 대입하는 변수는 추론하지 않습니다. classmethod 안의 Python `cls(…)`는 그 클래스를 부르는 호출입니다. 이름이 제품에 하나뿐이라는 이유로 푸는 것은 없습니다.
    - **생성.** `new C(…)`는 C를 가리키는 참조라서, 거기에 닿으면 생성자에 닿습니다. 제품 그래프가 읽으며, 공유 스캔의 호출 사실에는 더하지 않습니다(그것은 호출만 담습니다). 내장 클래스나 제품 밖의 클래스면 그 이유로 셉니다. 타입 인자를 적은 TypeScript 호출(`make<T>(x)`)은 호출로 보지 못합니다.
    - **값 바인딩.** 함수식이 아닌 값에 묶인 모듈 수준 이름(`const fail = failWith("X")`)은 스캔한 코드 어딘가에서 불릴 때 종류 `값`, ID `<file>#<name>`인 코드 노드가 됩니다. 호출은 그 노드로 풀리고, 그 노드의 참조는 초기값 안의 호출이라 닿는 길이 만드는 함수까지 이어집니다. 아무도 부르지 않는 값 바인딩은 노드가 아닙니다.
    - **다시 내보내기.** 들여온 모듈이 그 이름을 선언하지 않으면 `export { a as b } from`, `export * from`, import한 이름을 적은 지역 export 목록(`export { j }`), default 내보내기(`export { default } from`), 그리고 Python에서는 패키지 모듈이 들여온 이름을 따라 선언까지 갑니다. 단계 수에 한도가 있고 고리는 원래 이유를 둡니다. `export * as ns from`은 읽지 않습니다.
    - **내장 호출.** 세 이유를 기계적으로 정합니다. 언어·런타임 네임스페이스의 멤버(`JSON.parse(x)`), 내장 함수나 생성자(`String(x)`)는 파일이 그 이름을 선언·들여오거나 묶지 않을 때만이고, 제품 어디에서도 정의되지 않은 이름의 메서드(`items.map(f)`)는 제품 코드일 수 없습니다. "정의"는 일부러 넓게 봅니다. 스캔한 코드 안의 어떤 메서드, 클래스 필드, 어느 객체 리터럴의 멤버, 시그니처, 따옴표 이름, 속성이나 prototype에 대입한 함수, defineProperty 이름이든, 선언이든 아니든 셉니다. 실행 중에 만든 이름(`obj[name] = fn`)은 보지 못합니다. 제품이 `map`을 직접 정의하면 그 호출은 받는 쪽 타입을 모르는 이유에 남습니다. 이름 표는 언어마다의 판단이고, 프로젝트 규칙으로 늘립니다. 그 규칙은 `"내장 이름"` 아래에 적고, 그 항목은 `호출 방식 표.json`에 둡니다.     - **매개변수나 지역 변수에 담긴 함수.** 이름이 감싼 함수의 매개변수나 지역 변수인 평범한 호출(`handler()`)은 따로 된 이유로 세고 연결을 만들지 않습니다. 무엇이 담기는지는 데이터 흐름 분석이 있어야 압니다.
    - **세 수.** 한계 블록은 전체 호출, 제품 코드일 수 없는 호출(내장 이유와 언어 키워드)과 제품 밖 모듈로 가는 호출, 그리고 제품 코드일 수 있는 호출 중 풀린 수를 적습니다. 모든 호출은 여전히 이유 하나에만 세고, 이유들의 합은 전체와 같습니다. 받는 쪽 타입을 모르는 이유는 이제 메서드 이름이 제품에 있고 받는 쪽을 모른다는 뜻만입니다.
