# Notion·Obsidian 작업 문서

[English](../work-document-projection.md)

선택한 작업을 문서로 정리해 달라고 요청하세요. 같은 정확한 원기록에서 사람용 설명과
에이전트용 Markdown을 만듭니다. 이유·대안·조건·결과·남은 일·미확인을 함께 제공합니다.
새 사용자 승인·Product Canon·체크포인트·완료 판정이 되는 문서는 아닙니다.

로컬 미리보기에는 Product 온보딩·World 재구축·내보내기·Run·Todo 도입이 필요하지
않습니다. Todo 없는 기존 작업도 정확한 원기록과 명시적 작업 연결로 선택합니다.
도구 인자는 Lode가 채우므로 사용자가 JSON을 작성할 필요는 없습니다.

연결할 때 vault나 Notion 부모 페이지와 자동 갱신할 태스크 범위를 지정합니다.
연결 자체는 게시하지 않습니다. Notion은 명시적으로 선택한 Host 환경 변수 참조만
저장하며 토큰 저장·주변 자격증명 탐색을 하지 않습니다. 미연결이 일반 작업을 막지
않습니다. 실제 게시에는 현재 유효한 목적지·내용 범위의 사용자 권한이 필요합니다.

## 문서가 놓이는 곳

모든 게시물은 vault의 `Lode/` 안(또는 지정한 Notion 상위 페이지 아래)에 제품마다 하나인
읽기 쉬운 트리로 들어갑니다.

```
Lode/
└─ <product>/
   ├─ <product>.md
   ├─ 근거/
   ├─ <feature group>/
   │  ├─ <feature group>.md
   │  ├─ 근거/
   │  └─ <feature>/
   │     ├─ <feature>.md
   │     ├─ <task title> 결과 1.md
   │     ├─ <task title> 결과 2.md
   │     └─ 근거/
   ├─ 소속 미확인/
   ├─ 결정과 조건/
   └─ 작업 기록/
```

폴더마다 폴더 이름과 같은 문서(제품·기능군·기능 문서)가 하나 있습니다. 게시한 결과는
결과마다 새 파일 `<task title> 결과 N.md`이며 한 번 쓴 뒤 다시 쓰지 않습니다. 다음 결과는
이전 결과 링크로 이어집니다. 모든 문서의 에이전트용 짝은 같은 폴더의 `근거/` 안에
`<document name> 근거.md`로 있습니다.

이름: 제품은 프로젝트 문서에 지정한 프로젝트 제목, 없으면 프로젝트 폴더 이름입니다.
기능군·기능은 제품 모델의 이름을 씁니다. 파일 이름에 쓸 수 없는 글자는 빼고 40자에서
자르며, 같은 폴더에서 다른 Lode 문서나 사람이 만든 파일이 이미 그 이름을 쓸 때만
`(d403)` 같은 짧은 꼬리표를 붙입니다. 지정한 Notion 상위 페이지 아래에 이미 있는 페이지
제목도 다시 쓰지 않습니다. Lode가 만든 페이지 안에서는 Lode의 이름끼리만 비교합니다. vault 기준 경로는 180자를 넘지 않습니다. 깊은 기능군은 더 얕은 자리에
두고 상하 관계는 링크로 남깁니다.

배치 규칙:
- 여러 기능군에 속한 기능(또는 상위가 여럿인 기능군)은 제품 모델 파일에 먼저 적힌 상위
  아래에 폴더 하나만 두고, 다른 상위의 문서에서는 링크로 이어집니다.
- 여러 기능에 걸친 결과는 첫 번째 기능 폴더에 파일을 두고 나머지 기능 목록에 링크로
  나옵니다.
- 기능을 지정하지 않았거나 제품 기능이 아닌 키를 지정한 결과는 `소속 미확인/`에
  놓입니다. 받지 않은 키는 준비·게시 결과에 알립니다.
- 기능군 없는 기능은 제품 폴더 바로 아래에 둡니다. 제품 모델이 없으면 제품 폴더와
  `소속 미확인/`만 생깁니다.

기능은 Lode가 준비할 때 고릅니다. `lode_work_document_prepare`의 `feature_keys`(또는
`document_selection`의 `featureKeys`)에 제품 모델의 기능 중에서 고른 키를 넘기며, 사용자가
말한 기능이 있으면 그것을 씁니다. 이것은 읽기용 연결일 뿐이며 제품 모델은 바꾸지 않습니다.

폴더 위치는 처음 만들 때 정해 목적지마다 기록합니다(기능 → 폴더 표). 제품 모델에서 기능
이름이나 소속이 바뀌어도 폴더와 파일은 그대로 두고, 제목과 링크 글자만 새 이름을 따르며
새 결과도 기존 폴더에 계속 놓입니다. 결과 게시는 그 기능의 문서와 현재 상위 문서까지 함께
맞추고, 떠난 이전 상위 문서와 그 기능을 나열하는 결정 문서는 다음 프로젝트 게시가 갱신합니다.

### 사람이 읽는 내용

결과 문서는 제목, 상태와 기록 시각(UTC), 한 일, 판단과 이유, 남은 일, 확인하지 못한 것,
맺음 링크 한 줄(이전 결과·기능·근거 문서)로 이루어집니다. 사람용 문서에는 identity 줄·
표시 줄·해시·식별자·내부 코드·반복 안내·주석이 없습니다. 근거 문서는 `관리 정보` 구역으로
시작합니다. 읽기용 사본 안내, 두 문서의 식별자, 프로젝트·세션·작업, 결과 번호, 근거
기록, 기준 해시, 이전 결과, 문서 규칙과 배치 방식 버전이 들어 있고, 그 아래에 정확한
원문·비교·인용·그래프 근거가 이어집니다. Lode는 `관리 정보`를 다시 읽어 판단하지 않습니다.
기준은 Lode 기록이며 게시 뒤 확인은 문서 전체를 비교합니다.

기능 문서의 이 기능의 결과 같은 목록에는 표시 줄이 필요 없습니다. Lode는 마지막으로 써
넣은 목록 글을 기록하고, 그 글이 문서에 정확히 한 번 있을 때만 바꿉니다. 사람이 목록을
고쳤으면 그대로 두고 `personEdited`로 알리며 결과 게시는 그대로 끝납니다. Lode가 마지막에
쓴 그대로인 문서는 제목·설명까지 통째로 새로 쓸 수 있습니다. 문서는 파일이 아니라 글로
판단하므로, 편집기나 동기화 도구가 임시 파일로 다시 저장해도 바뀐 것이 없습니다. 사람이
지우거나 이름을 바꾼 폴더 문서는 `document-missing-not-recreated`로 알리고 결과 게시는
계속하며, Lode가 다시 만들지 않습니다. 파일을 되살리면(vault 휴지통이나 이름 변경 되돌리기)
돌아오고, 마지막 목록 글이 다시 보이면 Lode가 목록을 다시 갱신합니다. 사람이 Lode 폴더 안에
만든 파일은 건드리지 않으며, Lode가 만들려던 이름에 사람의 파일이 있으면 덮어쓰지 않고
`occupiedPath`와 함께 `WORK_DOCUMENT_NAME_OCCUPIED`로 알립니다. 사람이 그 파일을 옮기거나
이름을 바꾸면 풀립니다. 그때까지 그 문서는 쓸 수 없으며, 제품 문서라면 그 vault로의 게시
전체가 멈춥니다. vault 파일에서 확인하지 못한 변경은 글로 정리합니다. 이전 글이 그대로면 지금
쓰고, Lode의 새 글이면 이미 된 것이며, 그 밖이면 사람이 고친 것으로 보고 그대로 두고 알립니다.
작업별 시작 문서와 메모 문서는 없습니다.

### 프로젝트 문서

“프로젝트 문서를 제품 → 기능군 → 기능 순서로 정리해 줘”라고 요청하세요. 선택적
`projectDocuments` 범위가 있으면 프로젝트 게시가 제품·기능군·기능 문서(설명, 관련 결정,
원문에 연결한 설명), `결정과 조건/`(결정·요구·제약·역량·정책마다 문서 하나),
`작업 기록/`(선택한 작업 기록, 최근 것부터)을 채웁니다. 여기서 제품은 기존 Project의
읽기 루트이며 새 정본 엔티티가 아닙니다. 여러 기능에 걸친 결정·작업은 같은 원문을
링크합니다. 설명은 인용한 원문에 고정되며 제품 모델이 바뀌면 Lode가 갱신할 때까지 이전
원문에 대한 설명임을 표시합니다.

프로젝트 문서에 선택한 작업 읽기는 게시된 결과로 연결됩니다. 결과는 Lode가
`lode_work_document_publish`로 게시하며 자동 게시는 둘 다 합니다. `projectDocuments`는
기존 연결 대화에서 지정합니다. 업데이트가 작업별 연결을 넓히지 않으며 사용자 JSON·Todo·
온보딩 절차를 더하지 않습니다. 기존의 풍부한 근거 선택은 Lode가 유지하거나 의식적으로
수정하며 최근 메모 하나로 몰래 줄이지 않습니다.

같은 실제 Notion 부모나 물리 vault의 다른 연결 별칭·세션은 트리 하나를 함께 씁니다.
제목이 같은 다른 프로젝트는 서로 다른 폴더를 갖습니다. 큰 제품은 제한된 호출로 이어서
게시합니다. `continuation-required`는 Lode가 이어갈 일이며 사용자 작업이 아닙니다. 게시가
여러 호출에 걸치는 동안 제품 문서에 갱신 중이라고 표시합니다. 이 줄은 그 게시만 지웁니다.
마지막 호출에서, 또는 원문이나 선택이 바뀌어 그 게시가 거부될 때입니다. 목적지의 연결이나
설정이 바뀌었으면 Lode는 그곳에 아무것도 쓰지 않으며, 쓸 수 있는 다음 게시가 줄을 바꿉니다.
이 줄은 Lode 목록 구역에 있으므로 사람이 고친 제품 문서에서도 지웁니다. 결과는
다시 쓰지 않으므로 그 밖의 문서는 이전 사본을 따로 남기지 않고 제자리에서 갱신합니다.
선택한 모든 문서를 확인한 뒤에만 완료입니다. **동시 원격 CAS를 보장하지 않으며** receipt는
마지막 확인 범위입니다. 오래된 원문·설정은 거부하고 제품 모델 읽기 실패는 원래 실패를
유지합니다. 읽을 수 없거나 선택하지 않은 세션의 기여를 몰래 지우지 않습니다.

### Notion

Notion에는 지정한 상위 페이지 아래에 같은 트리를 페이지로 만듭니다. 제품·기능군·기능·
결과 페이지가 있고, 각 페이지의 근거 페이지는 그 아래 `근거` 페이지 밑에 둡니다. 페이지
제목은 vault 파일 이름에서 `.md`를 뺀 것이며 사람용 페이지에는 identity 줄이 없습니다.
페이지 만들기 결과를 알 수 없을 때는 정확한 상위 페이지 아래에서 제목과 본문이 모두 같고
다른 문서로 기록되지 않은 페이지가 정확히 하나일 때만 그 페이지를 잇습니다. 그렇지 않으면
멈추고 알리며 중복으로 만들지 않습니다. 생성 유실 뒤 검색이 여러 호출에 걸치면 일치
페이지도 후보 관측으로만 남고 현재 유일성을 증명하지 않습니다. 새 트리의 첫 게시는 한
호출의 요청 예산을 넘을 수 있습니다. 이때 결과는 `continuation-required`이며 같은 준비
결과를 다시 게시하면 끝난 단계를 유지한 채 이어갑니다. 결과를 알 수 없는 페이지 생성의
복구는 한 호출의 요청 예산 안에서 상위 페이지를 끝까지 나열하고 읽어야 합니다. 그럴 수 없으면
(큰 상위 페이지, 또는 그 호출에서 이미 다 쓴 예산이나 시간) 목록을 처음부터 다시 시작하게 될
반복 대신 `recoveryLimit`으로 알립니다.

### 이전 게시물

이 배치 이전에 게시한 문서(`Lode/<Project>/<Session>/<task-key>/`와
`Lode/<Project>/ProjectDocuments/`)는 옮기지도, 이름을 바꾸지도, 지우지도, 다시
기록하지도 않으며 옛 방식으로 게시된 것으로 읽습니다. 그런 작업의 다음 결과는 새 트리에
놓이고 이전 결과 링크가 옛 사람용 문서를 가리킵니다. 그때 옛 시작 문서의 Lode 목록
구역을 새 위치로 가는 링크로 한 번만 바꿉니다. 사람이 그 구역을 고쳤으면 건너뛰고
알립니다.

### 의미

‘현재’는 문서와 필수 링크를 다시 읽어 확인한 마지막 근거입니다. 미게시 로컬 변경 전체·
태스크 완료·배포·모든 원문의 최신성을 뜻하지 않습니다. Typed MCP는
lode_project_document (prepare, publish, status), CLI는 project-document-prepare,
project-document-publish, project-document-status입니다.
document-projection/project/<Project>/의 P5 게시 기록은 세션 P2 방향을 합치지 않습니다.

중요한 취소·미실행 검사·모순은 두 문서에 모두 남깁니다. 작성자의 합의 요약은 실제 사용자
발언이 아닙니다. 해시 일치는 의미상 최신성을, 과거 검사 통과는 현재 코드의 검사 통과를
뜻하지 않습니다. 실제 전후 바이트가 있을 때만 근거 문서에 제한된 비교를 싣고, 없으면 diff
미확보를 밝히며 지어낸 diff로 채우지 않습니다. 그래프 관계는 탐색에 쓰고 승인·구현 충족·
인과로 바꾸지 않습니다. 로컬 경로는 근거 식별자이며 원격 접근을 보장하지 않습니다. 전체
대화·provider 세션 ID·로컬 절대 루트는 복사하지 않고 세션 체크포인트도 자동으로 내보내지
않습니다.

## 자동 갱신·재시도

비동기 CLI/MCP `session-work-record` 조합은 기존 create-only P3 원문부터 저장합니다.
명시적으로 연결한 단일 범위 태스크 결과이면 관련 문서를 준비합니다. 이후 partial·
waiting·cancelled·정정은 그 작업의 다음 결과로 게시합니다. 앱 종료·idle·체크포인트 저장·빈 pending·단독
`completed` 표기는 완료 근거가 아닙니다. 혼합 태스크나 불완전·충돌 revision은 게시만
미확정으로 두며 작업 저장은 유지합니다. 변화 없는 재시도는 중복 문서를 만들지 않습니다.

동기 `recordSessionWorkEvidence` API는 동기입니다. 체크포인트 sync와 무관한 저장에는
외부 게시를 추가하지 않습니다. 단일 Todo 없는 작업은 명시 생성할 수 있으며 필수
Todo·저장 의식으로 바꾸지 않습니다.

동일 결과 재시도는 확인한 근거·diff·인용·관련 기록·그래프 선택을 재사용합니다.
최근 기록 하나로 몰래 축소하지 않습니다. 새 revision에서는 같은 비동기 record 호출에
선택적 `document_selection`을 함께 전달할 수 있습니다(CLI `--document-selection`).
그 요청의 `recorded` 별칭은 저장된 정확한 원문으로 해소하며 P3 스키마나 권한을
바꾸지 않습니다. 기존 풍부한 범위를 Lode 판단 없이 안전하게 이을 수 없다면
`lode-selection-required`, 기록된 재개·취소, 원격 미갱신 상태를 반환합니다. Lode가
제공된 정확한 이전 범위를 참고해 같은 턴에서 명시적 준비·게시를 끝냅니다. 사용자
양식이나 작업 재저장을 요구하지 않습니다. 이전 before/after는 새 기록의 선택으로
명시하지 않는 한 과거 비교이며 새 변경으로 자동 재해석하지 않습니다.

실질적인 분석 결과 글은 유효한 P3 본문만으로 게시할 수 있으며 외부 파일 첨부가
필요하지 않습니다. 태스크명·상태만 있고 결과 내용이 없으면 미확정입니다. 이는 내용의
존재 확인이며 의미적 충분성·실행 성공·승인 판정이 아닙니다. 원문 파일이 없으면 두
뷰에 정확한 실패 코드를 남기고 보존 바이트와 현재 파일을 구분합니다. 불가능한 비교와
인용은 unknown으로 유지합니다. 원본 P3 소유·digest 실패는 근거 검증 실패이며 원문
접근 거부를 다른 reader로 우회하지 않습니다. 텍스트 전용 CLI/MCP 응답에도 구조화
응답과 동일하게 게시 상태와 Lode의 제한된 준비·게시 후속 작업을 전달합니다.
문서 게시 효과와 원래 작업 효과를 구분합니다.

효과 전에 시도 기록을 저장합니다. 생성 응답 유실은 그 기록과 선택 부모의 제한된
목록에서 본문·부모를 정확히 대조합니다. mapping 유실·복사 페이지·중복 일치·task 만료·
빈/부분 목록은 POST 재발행 근거가 아닙니다. vault 파일은 정확한 이름으로 정리합니다(없으면
만들고, Lode의 글이면 잇고, 다른 글이면 그대로 둡니다). 일치 사본도 최초 생성 사건·저자 권한의
증거가 아닙니다. 과거 exact ref를 같은 제목의 새 페이지에 연결하지 않습니다.
알려진 async task는 terminal 성공과 readback을 요구하며 warnings 부재만으로 성공
처리하지 않습니다. 한 목적지 실패는 다른 목적지 receipt를 지우지 않습니다. 게시만
재시도하고 원래 작업 효과는 다시 실행하지 않습니다.

Notion 페이지 생성·정확한 Markdown 교체에서 정상적으로 일치하는 `403` /
`restricted_resource` 응답은 결과 불확실과 구분해 요청 거부로 기록합니다.
이 코드는 권한 부족뿐 아니라 workspace 블록 한도일 수도 있어 원인을 그대로 남깁니다.
원인을 고쳐도 자동 재시도하지 않습니다. 현재 권한 범위 안에서 Lode가 반환된 정확한
시도 참조를 `retry_rejected_writes`(CLI 입력 `retryRejectedWrites`)에 전달하면 동일
요청의 후속 시도 한 번을 만듭니다. 이전 시도·결과는 create-only로 보존합니다.
다시 거부되면 새 참조가 필요하며 중복 클릭은 후속 시도를 추가 생성하지 않습니다.
부모·method·내용·설정·원문 근거·현재 관리 본문이 여전히 일치해야 합니다.
원문이 바뀌면 Lode가 새 문서 쌍을 준비합니다. 트리 문서의 생성 요청 자체가
완전히 같다면 확인한 새 근거에서도 이전 거부 참조를 이어 쓸 수 있습니다.
과거 뷰·바뀐 쓰기 본문·오래된 준비 근거를 재사용하는 것은 아닙니다.
사용자 JSON이나 원래 작업 재실행을 요구하지 않습니다. Host 거부 우회·다른 계정 전환·
자동 record hook에서의 묵시적 재시도는 허용하지 않습니다.

HTTP 숫자·오류 문구·호출자 플래그만으로는 판정하지 않습니다. 비정상·불일치 오류,
응답 유실·5xx·async 실패·시간/용량 제한·거부 증거 저장 실패는 결과 불확실이며 새
쓰기를 허용하지 않습니다. 재시도 응답이 유실되어도 같은 readback 전용 복구를 따릅니다.
거부 기록은 P5 운영 증거이며 실행 허가나 복구 방향 결정이 아닙니다.

Notion 게시·복구 한 번의 전체 예산은 30초·64요청이며 응답은 수신 중 4MiB를
제한합니다. 의미적 컨텍스트나 일반 작업 제한이 아닌 선택적 전송 예산입니다.
소진되면 효과를 미확정으로 보존합니다. 상주 daemon 없이 다음 요청에서 알려진
대기를 이어갈 수 있습니다.

## 소유·동시 편집

Obsidian은 선택 vault의 `Lode/` 안에만 씁니다. 새 문서는 exclusive create하고, Lode
문서는 Lode가 기록한 글(문서 전체 또는 목록 구역 하나)이 그대로 있을 때만 바꿉니다. Notion도 전체 교체 대신 단일 `update_content` 정확한 문자열 교체를
합니다. 관리 밖 내용은 보존하고 생성 뷰 편집은 drift로 표시하며 덮어쓰거나 정본으로
수집하지 않습니다.

목적지별 로컬 조정은 HTTP 중 Project mutation lock을 잡지 않습니다. 사전·사후 조회와
정확한 문자열 교체는 **원격 CAS가 아닙니다**. 임의 동시 편집의 무손실이나 두 목적지의
원자 게시를 보장하지 않습니다. receipt는 실제 확인 범위와 부분·미확정을 남깁니다.

## API·시험

Typed MCP는 `lode_work_document` (`configure`/`prepare`/`publish`/`status`)이고 `lode_work_` 그룹에서
찾습니다. CLI는 같은 `work-document-*`와 요청별 Session 경로를 제공합니다.
status는 로컬 receipt이며 실시간 네트워크 최신성 검사가 아닙니다.

공통 근거·뷰는 P4, 설정·시도·async 진행·receipt·교체 가능한 current 포인터는 기존
`document-projection/work/<Session>/`의 P5입니다. 논리 키·근거·렌더 뷰·링크 해소
payload·readback 해시를 구분합니다. 트리 기록(배치 방식 버전, 기능 → 폴더 표, 파일 이름,
마지막으로 써 넣은 목록 글)은 document-projection/project/<Project>/의 P5입니다. 기존 동기 GraphSnapshot Markdown 바이트 일치
계약은 유지합니다.

합성 vault와 fake HTTP로 검증합니다. 실제 Notion 정규화·권한·서비스 동시성은 live
검증이 필요합니다. 엄격한 readback과 다르면 미확정이며 fake 통과를 실서비스 통과로
주장하지 않습니다.
