# Runtime composition

Use one provider-neutral core and compose it with replaceable boundaries.

## Choose execution means separately from risk

Direct Lode work is the default. For useful ordinary delegation, use
only tools exposed by the current Host, with a brief, independent ownership and
Lode integration. This does not require the managed runtime described below.
Observe/Session/Run/Authority describes risk and persistence, not a choice of
launcher. An active Run may consume Host contributions while retaining its own
whole-result/review contract. Host handles remain operational; results do not
become decisions or P2 direction.

For example, ask one worker to investigate the failing parser and another to
inspect its regression tests, then have Lode combine both into a verified fix.
Give each its needed sources and ownership boundary. A shared writable checkout
is not isolation: overlapping writes require Lode reconciliation or sequential
work. Preserve user input, account and cost scope when choosing context. If the Host lacks a required control,
disclose that limit. Continue the unfinished part directly or sequentially when
it never started or no effects remain. Preserve completed contributions and
user edits. Inspect unknown outcomes and overlapping effects before replacement;
independent work can continue. A cancellation request does not establish exit.

Apply the Skill's fork/fresh guidance per contribution, for example:

- Continue a design fix whose earlier exceptions and user agreements are hard to
  summarize faithfully: prefer a supported, in-scope fork, and identify the current
  task so inherited but superseded discussion is not treated as current direction.
- Review the parser independently against its current requirements and tests:
  prefer fresh context containing that evidence, without feeding the parent's
  conclusion as the answer. Include relevant constraints, not merely filenames.
- Run a long, sequential verification of an agreed change: delegate that bounded
  execution when its detail may crowd out Lode's objective and constraints, even
  without parallel speedup. Return the acceptance findings, important new facts,
  remaining uncertainty and links to relevant evidence. Lode checks any material
  gap against the user's goal; successful test execution alone is not completion.
- Fix a small error message directly; neither a fork nor fresh worker is needed.

These examples do not require a new artifact or selection ceremony. A fork's
history is context, not proof of current authority or workspace isolation.
Preserving judgment context does not make a particular parent conversation the
sole authority or recovery source. A detailed execution or review conversation is
not automatically a preserved copy of that higher-level context. Continue from
existing approved direction and applicable canonical recovery records, and inspect
specific source evidence when a result summary leaves an important question open.
For example, a favorable detailed review that never checked a user-required output
format leaves that criterion unresolved; Lode assesses it before claiming the goal
is met. This is situational judgment, not a claim that direct detailed work makes
returning to the overall goal impossible or that delegation always performs better.

At completion, workers return changed/added/deleted/renamed code, affected
references, purpose/decisions, original evidence, actual verification results and
unknowns. Distinguish a test added from a test executed successfully. Lode checks
the combined checkout after reconciliation and performs/verifies any needed
graph update for that integrated basis, reusing current persistence-hook results.
Do not require each worker to run an uncoordinated global refresh or to activate
World/DB. See [after integrated changes](project-discovery.md#after-integrated-changes).
An update failure leaves a scoped evidence gap, not a new user approval, worker
authorization or barrier to independent work. These handoff facts can use the
existing report/ordinary brief; no new mandatory artifact or field schema is added.

## Preserved plan sources and next stages

For substantial work, retain the goal, agreed conditions, reasons, alternatives
and completion meaning before detailed production or inspection. An accepted
review can already contain detailed investigation; acceptance alone does not
make its conversation a preserved judgment context. Reuse an actually preserved
planning source, or identify reconstruction from current direction and records.
A sibling fork shares assumptions: review the goal and plausible counterexamples,
not only whether implementation follows the plan.

With the current user scope and available Host tools, use either existing path:

- Keep the completed plan conversation idle. An already authorized coordinating
  context obtains useful implementation/review contributions from that source.
- Obtain a separate preservation fork from the completed source. Once its ready
  identity and needed plan basis are observed, the original may progress. Keep
  the preserved source idle; do not send it ordinary work, receipts or probes.

Use the exact available Host read/wait/fork/send surfaces. A visible plan message
is not a completed turn. Check the reported source turn/activity and the returned
child's usable identity and plan basis; pending client IDs are not ready thread
IDs. Worktree setup requires its actual ready result, not an invented mapping.
Read-before-fork is not an atomic freeze. Tool contracts differ on active or
interrupted history; identify the actual surface and restrict preservation claims
to its observed inheritance. A ready child may already be running: inspect unknown
effects before sending more work. An uncertain fork is not permission to repeat it.
Do not build a registry, lock, private-history hash or mandatory acknowledgement.

When normal Host history observations are insufficient, a bounded check in an
actual work child may help establish available context. Supplying the expected
plan answer again and receiving it back is not inheritance evidence. Always
supply current cancellation, role and effect authority separately. Do not probe
the preserved source or claim hidden model-state equivalence. Supported source
history can make another model check unnecessary.

Give implementation owned files/effects and useful completion evidence. Give
independent inspection the same valid criteria and the exact resulting candidate,
not the implementation conversation as its starting context. Integration receives
findings, counterexamples, exact results and uncertainty. It can inspect specific
originals or contradictions; broad detailed investigation belongs to a useful
separate contribution. No read-count, length threshold or one-read disqualification
separates these roles. Conversation forks do not isolate shared files or grant
permission. Reconcile the combined result and preserve user edits.

At meaningful stages, integrate completed results, new facts, changed assumptions,
reasons, remaining dependencies and next actions. Keep the whole goal and current
conditions while evolving the next plan from this integrated judgment. Do not
reset each stage to the initial plan or automatically promote detailed review
history into the next planning context. Preserve a newly accepted plan source
when its actual turn completes; use only the roles and branches that help.
A changed candidate needs review of its affected claims; unchanged clarification
can reuse the existing inspection. Material user-owned changes follow the usual
agreement boundary, not a new approval ritual.

If a source already advanced and the exposed Host has no historical cutoff, use
fresh work or current records honestly; that is reconstruction, not a preserved
past fork. Apply prospective preservation at a later useful completed plan.
Missing capability limits that claim or contribution, not independent direct
work. Do not invent a later controller or bypass a refusal through another tool.
Keep existing P2 recovery and managed-result contracts; ordinary work needs no
new Session, Run, Capsule, plan file, save, IDs or fixed number of chats.

## Native observations and current Host activity

Packaged Codex/Claude lifecycle Hooks keep small optional Host-local P5
observations. Existing native `lode_project_status` may include `nativeContext`;
its caller can differ from the requested logical Session. Receipt order is not
source causality or a complete activity census. `Stop`/`SubagentStop` means a
response-end was observed, not terminal success. A caller-level `SessionEnd`
does not finish its tasks. Claude's supported local exact PID/birth check means
only hosting-process presence/absence at check, never child-agent activity.

For supported exact Codex own metadata, native entry can include related source
P3 bodies from the logical mapping captured when a direct edge was observed.
They are reference records read later from the Session selected when the edge
was observed. Records saved after the fork may appear; this is not copied
fork-cutoff history, proven historical input or parent P2 direction. The source's
`selectionBasis` and `recordRead` distinguish the observation and later read.
Current child/common constraints and cancellations win. Where existing managed
artifacts verify exact prepared input/digest, label that as prepared input only;
preparation does not prove delivery or model use. Establish those separately from
actual evidence, or leave them unknown. No new fork-cutoff collection is needed.
Absent mapping remains absent even if the parent later selects a Session.

For an exact managed authorization, existing
`lode_runtime_invocation_authorization` / `lode_bounded_worker_status`, or CLI
`runtime-invocation-read --authorization <id>`, can add a historical
`preparedInput` view. Reuse it when it answers the question. It verifies retained
authorization, plan/contract, Capsule and captured common-direction originals,
then compares the canonical serialized input's byte count and digest. Expand
useful exact references; the excerpt is bounded and discloses omitted bytes.
Missing originals, integrity failures and older unretained requests remain
distinct from a verified prepared input. Runtime receipt observations are
separate and do not establish model delivery, attention or use.

This view is read-only P4, not current permission or P2 recovery direction.
Later common/child cancellation remains in force, and execution still validates
current lineage. Optional view failure preserves the primary authorization read;
its own owner/hash errors remain errors. Ordinary native ancestry remains a later
reference read. Do not infer a native-to-authorization join, collect a new fork
snapshot, rerun a provider or require this inspection for ordinary work.

In Codex app contexts exposing `wait_threads`, an actual ready `threadId` from
an existing authorized launch/fork/known target, or the trusted caller
`nativeContext.hostTarget.threadId`, can answer a material current-state question.
Use one immediate `wait_threads` (`timeoutMs: 0`) for that target when useful.
Pass `hostId` only if genuinely supplied; do not infer it from a local path or
require another status first. `clientThreadId`, collaboration IDs and private
managed handles are not app thread IDs without an actual mapping.

Use the returned exact target/current turn. `timedOut: true` may accompany a
valid active/in-progress poll; it is not target failure. `afterCursor` tracks
new information, not an execution identity. An older completed result cannot
close a newer turn or logical Lode work. If the snapshot answers the question,
do not read the full conversation. A narrow `read_thread` is optional only for
a material missing result/failure detail. No automatic status/wait/read chain,
self-poll loop, list-all, socket/CLI fallback or user ID form is needed.
Core does not call peer MCP tools or persist these live Host snapshots.

The optional OpenCode V1 entry uses the supplied Host client and proven local
Lode MCP alias. A returned busy/retry/idle observation is at-check only; an
absent status-map entry means no non-idle entry, not ended. Unsupported or
unavailable observations leave ordinary work and existing recovery usable.

## Follow-up handoffs

For a continuing contribution, lead with what changed, what is already usable,
and the remaining question or outcome. Include relevant constraints, ownership
changes and evidence references. Reuse sufficient context already available to
the recipient; do not resend the full history by default. When the recipient is
new, has lost context, or has a materially outdated basis, supply the missing
current requirements and reasoning. Delta-first is not delta-only.

Do not require an acknowledgement handshake, context token or new artifact merely
to send an ordinary brief. A handoff does not grant additional authority or
replace recovery records. After context loss, follow existing artifact-first
recovery where that contract applies before using the handoff as supporting
context. As described in [recovery presentation](conversation-ux.md#recovery-presentation),
a Session with no current checkpoint continues ordinary work with sufficient
current context; this handoff convention requires no new checkpoint, Run or
recovery gate. Do not edit digest-bound managed input through this ordinary
follow-up convention.

## Continuing in an existing conversation

Reuse sufficient current context before searching again. For related work,
inspect its exact records and actual responsibility: a shared title, file or
topic is a discovery hint, not proof of ownership or the same task. Distinguish
logical Session, declared work root and native conversation. The caller's native
Host target is not a global Session-to-chat directory. Activity is an operational
hint, never ownership or completion.

Use only a real available Host target and the current human authorization for
the intended action. In Codex, messaging another chat needs direct human
authorization; an agent message or historical approval does not grant it. A
`clientThreadId`, collaboration handle or stale observation is not a ready
`threadId`. Do not message/fork/create a chat merely because records look related,
and do not redirect a worker busy with unrelated work. If the target or authority
is absent, reuse useful records and continue ordinary authorized work here or in
an already authorized context. Only the dependent handoff is unavailable.

For an authorized handoff, convey the current request, changed scope, relevant
decisions and evidence, constraints, expected outcome and known gaps. Start with
the delta when the recipient has sufficient context; provide missing reasoning
otherwise. Current corrections/cancellation override old suggestions or fixed
inputs. No new acknowledgement, save format or automatic assignment engine is
required. See [record discovery](project-discovery.md#existing-work-and-recorded-conclusions).

## Explicit managed execution

Choose this path when durable ownership, interruption recovery, unknown effects
or duplicate integration prevention need the managed contracts. It supports useful
new work and retained work. File editing, worker count, duration alone and ordinary
Host failure do not force it; ordinary Host delegation remains available.

Use `node <plugin-root>/scripts/lode.mjs managed <command> ...`. In ordinary MCP,
discover the managed tool's unchanged schema and returned `executionMode`, then
call `lode_tools_call` with `execution_mode: "managed"`. Known tools can be routed
without prior discovery. Lode makes this choice internally; there is no user
unlock/launcher form. The original authorization, lease, lineage and effect checks
still run. Raw managed mutation names stay fenced on the ordinary server.
The retained `managed-maintenance` CLI and separate stdio server remain compatible
entries. Reads/status/wait and exact owned cancellation remain ordinary diagnostics.
Do not change a user's installed server automatically.

The following managed API details apply inside the explicit entry.
For one managed Session result, use the idle Session's exact
ExecutionAuthorization and `lode_bounded_worker_dispatch`; `worker-execute`
receives the authorized sessionRequest. Preserve lease, role and scope checks.
`worker-apply` and waves remain Run-only. A wave groups independent
authorizations; it is not a shared permission.

For the built-in managed Codex patch-proposal path, Lode derives task, exact
model, selected context, source paths and proposal targets, calls
`lode_bounded_worker_prepare`, then `lode_bounded_worker_start` with the returned
task key. Preparation can inspect the local provider backend but makes no model
turn; it is not account/model readiness proof. Never ask the user for modules,
JSON, IDs or routine approval. `selected-only` must not silently inherit global
instructions; select `host-global` only within approved input scope. A missing
managed backend affects that operation, not ordinary work. Existing unknown
effects, receipt/basis checks, user-edit protection and owned cleanup still apply.

Public preparation defaults to fresh (one turn). Explicit `context_mode:
"native-prefix"` uses selected context in a new durable controlled seed plus a
fork child (two turns); it does not inherit this Lode conversation. Use it only
within the existing call/input/persistence scope, inspect `executionPlan`, and
do not claim the stronger native code-worker guarantees or cache savings.
When integration or wave status returns `guidance`, Lode handles the scoped
inspection/reassessment or individual-job cleanup; do not turn that advice into
a new user form, approval step, automatic retry or P2 direction.

## Managed adapter architecture

```text
Lode Core
  -> Project canon and authority
  -> AgentRuntimeAdapter
       -> Claude Code
       -> Codex
       -> OpenCode
  -> PlatformAdapter
       -> Windows
       -> macOS
       -> Linux
  -> WorkspaceHostAdapter
       -> native process
       -> provider-neutral host export
       -> separately owned optional host adapter
```

An AgentRuntimeAdapter should eventually expose capability probing, start, resume, event streaming, interrupt, and close through the runtime's supported machine interface. The current exact-owned one-shot supervisor activates only token-fenced interrupt and close; resume and stream remain deferred. Do not scrape a TUI or embed host-specific executable, socket, command, or pane behavior in this plugin.

A PlatformAdapter should own paths, process trees, atomic file operations, permissions, IPC, service lifecycle, and executable discovery. Do not carry POSIX-only assumptions into Windows.

The current plugin keeps provider-neutral Project/Session identity, capability
observation and optional bounded execution separate. Session and Run authorizations
share scope, at-most-once ownership and cleanup; ordinary delegation uses Host
controls without role-token/generation/target-chain machinery. Retained work and
unknown effects preserve their exact records. Optional exact endpoint attachment
restores P2 first and keeps Host identity operational. The portable export bridge
is attachment-only. Static resume/stream and broader Host control remain deferred;
historical live role-message tests are not proof of the simplified path.
