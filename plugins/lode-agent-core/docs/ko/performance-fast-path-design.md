# 철학을 보존하는 빠른 경로

상태: 쿼리 전용 읽기 배치와 아래에 명시한 저장·coverage 최적화는 구현됐습니다.
나머지 절은 구현 설계 단계입니다. 어떤 빠른 경로도 사용할 수 있거나 더 빠르다는 이유만으로 권한을 갖지 않습니다.

이 설계는 두 번째 진실의 원천을 만들지 않으면서 중복 전송, I/O, 파싱 및 정규화를 줄입니다.
[`architecture.md`](architecture.md),
[`authority-plane-contract.md`](authority-plane-contract.md),
[`world-model.md`](world-model.md),
[`context-compiler.md`](context-compiler.md)와 함께 읽으십시오.

## 목표

운영 작업을 줄이면서 동일한 정식 결과, 식별자, 제외 항목, fallback 결정 및 fail-closed 오류를
반환합니다. 성능은 P5에만 속합니다. P1 Product Canon과 ReviewDecision, P2 복구 계보, P3
증거와 디스패치, P4 재구축 가능한 그래프 및 연속성 의미는 바뀌지 않습니다.

참조 JavaScript 구현은 계속 의미론적 기준입니다. 빠른 경로가 후보 결과를 생성할 수는 있지만,
기존 검증기가 최종 승인 경계로 남습니다.

## 비목표

- 새로운 Product Canon, 복구, 검토, 지시 또는 실행 권한을 만들지 않음;
- 공급자, 호스트, 데이터베이스, 저장소 또는 fixture에 특화된 동작을 만들지 않음;
- 백그라운드 서비스, 지속 작업자 또는 숨겨진 장기 실행 데몬을 만들지 않음;
- 경로 메타데이터나 watcher 이벤트만을 근거로 소스 바이트 최신성을 판단하지 않음;
- 전체 Context 후보 목록, 제외 항목, 점수 또는 순서를 바꾸는 top-k 사전 필터를 만들지 않음;
- 의미 식별자에 벤치마크, 지연 시간, 캐시, PID, 엔드포인트, 자격 증명 또는 물리 어댑터 필드를
  넣지 않음;
- 무결성 실패를 숨기거나 모호한 효과를 반복하는 최적화 전용 재시도를 만들지 않음.

## 보편적 빠른 경로 불변 조건

하나의 정식 입력과 생산자 버전에 대해 다음이 성립해야 합니다.

```text
reference(input).semantic == verify(fast(input)).semantic
reference(input).identity == verify(fast(input)).identity
reference(input).failure  == verify(fast(input)).failure
```

운영 진단은 다를 수 있습니다. 두 응답에서 진단을 제거하면 정식 출력이 깊은 수준까지 동일해야
합니다. 불일치가 있으면 빠른 경로를 비활성화하고 적합성 게이트를 실패시킵니다. 더 빠른 결과를
선택하지 않습니다.

## 구성요소 A: 운영 프로브

`OperationalProbe`는 선택적인 호출자 소유 수집기입니다. 정식 페이로드 밖에서 다음과 같은
제한된 카운터와 지속 시간을 기록합니다.

- 정확한 자식 프로세스 실행 횟수;
- HTTP 읽기 요청 수;
- 읽은 파일 및 바이트 수;
- 해시한 바이트 수;
- 파싱했거나 의미론적으로 재사용한 파일 수;
- 한 범위 안에서 재사용한 검증된 읽기 수;
- 구축했거나 재사용한 후보 설명자 수;
- 이름이 지정된 단계별 지속 시간.

프로브에는 내용에서 파생된 식별자가 없고, 기본적으로 지속되지 않으며, 의미론적 빌더에 절대
전달되지 않습니다. 정상 작업은 프로브를 할당하지 않습니다. 벤치마크에서만 명시적으로 만듭니다.

## 구성요소 B: 쿼리 전용 GraphDB 읽기 배치

기존의 정확한 자식 프로세스는 계속 구성된 환경 참조 이름에서만 자격 증명을 해석합니다. 제한된
배치는 `query` 작업을 하나부터 여덟 개까지 허용하고 명령이나 데이터베이스 수명 주기 작업은
허용하지 않습니다. 준비된 경로는 이미 검증된 현재 포인터를 읽은 후 토폴로지 매니페스트와 제한된
순회를 위해 이를 사용합니다. 포인터 검사를 분리해 두면 기존 fallback/stale 결정과 일회성 포인터
토큰이 보존됩니다. 호환되지 않는 프로토콜, 지원되지 않는 작업, 과도한 입력/출력, 과도한 쿼리 수
및 과도한 timeout은 거부됩니다.

자식 프로세스는 제한된 신뢰할 수 없는 응답 봉투를 반환한 뒤 종료합니다. 그러면 부모는 기존의
독립적인 포인터, 매니페스트, 순회, 요청 결속 및 영수증 다이제스트 검증기를 적용합니다. 포인터가
없으면 공개된 embedded fallback을 유지합니다. 오래된 포인터에는 기존 stale 오류를 유지합니다.
배치 출력이 누락되었거나, 부분적이거나, 순서가 바뀌었거나, 중복되었거나, 다이제스트가 유효하지
않거나, 그래프와 일치하지 않으면 fail-closed로 실패합니다. 전송을 사용할 수 없을 때는 기존에
문서화된 fallback 정책만 따릅니다. 무결성 실패는 절대 조용히 fallback하지 않습니다.

JavaScript exact child는 참조 전송입니다. 별도의 Go exact child는 계산 작업자 계약에 들어가지
않으면서 동일한 읽기 전용 프로토콜을 구현합니다. 설치된 네이티브 아티팩트에는 내용 주소화된
브리지 매니페스트가 포함되며, 검증된 플랫폼 바이너리만 자동으로 선택됩니다. 네이티브 아티팩트가
없으면 `auto` 모드에서 JavaScript 참조 경로를 사용합니다. 시작 또는 잘못된 출력 실패 시 `auto`
모드는 공개된 운영 진단과 함께 해당 경로를 사용할 수 있지만, `required`는 이를 거부합니다. 최초
또는 선택 후 매니페스트/바이너리 무결성 실패는 항상 fail-closed로 실패합니다. exact child는
선택된 비밀 참조와 제한된 운영 환경 allowlist만 받습니다.

전송은 해당 기능을 운영 메타데이터로 알립니다.

```json
{
  "preparedReadBatchProtocolVersion": "0.1.0",
  "preparedTraversalBatchAuthorityEffect": "none"
}
```

해당 기능이 없는 어댑터는 현재 요청 경로를 사용합니다. 어떤 정식 GraphSnapshot,
TraversalQuery, TraversalResult, Context Capsule 또는 오류 코드도 기능 가용성에 의존하지
않습니다.

## 구성요소 C: 요청 범위 검증 읽기

`VerifiedReadScope`는 하나의 최상위 동기 작업 동안 존재합니다. 같은 작업에서 반복해 읽게 될
이미 검증된 Product Canon, 프로젝션, 포인터 및 World Model 읽기를 메모화할 수 있습니다.

이 범위는 다음을 수행합니다.

1. 프로젝트 루트 하나를 해석하고 결속합니다;
2. 정확한 원시 경계 바이트와 검증된 식별자를 캡처합니다;
3. 불변 값 또는 방어적 복제본을 반환합니다;
4. 권한을 변경하는 쓰기에서 사용하지 못하게 합니다;
5. 최상위 결과를 반환하기 전에 경계를 다시 읽습니다;
6. 경계가 바뀌면 메모화된 값을 모두 폐기하고 한 번 재시도합니다;
7. 재시도에서도 경계가 바뀌면 안정적인 읽기 중 변경 코드로 fail-closed 실패합니다;
8. 작업과 함께 종료되며 절대 직렬화되지 않습니다.

`--fresh`는 재사용을 우회합니다. 프로젝트가 최신이라는 프로세스 전역 단정은 금지됩니다. 요청
간 캐시 작업에는 동일한 바이트 수준 최신성을 보존하는 별도 증명이 필요하며 이 설계의 범위 밖입니다.

## 구성요소 D: 단일 패스 저장소 검사

저장소 최신성 검사는 계속 모든 적격 경로를 다시 발견하고 모든 적격 파일의 실제 바이트를
해시합니다. 한 번의 패스로 해당 다이제스트를 검증된 이전 스캔과 비교합니다.

```text
discover -> read bytes once -> hash -> compare prior digest
                                      | equal: reuse validated analysis
                                      | changed: parse current bytes
                                      | new: parse current bytes
after discovery: record removed paths -> canonical sort -> validate result
```

이는 먼저 전체 최신성 읽기를 수행한 다음 두 번째 전체 스캔을 수행하는 변경 상태 시퀀스를
대체합니다. 경로 크기, 타임스탬프, 파일 ID, 파일 시스템 이벤트 및 watcher 세대는 운영 진단에
나타나거나 작업을 제안할 수 있지만, 현재 내용을 증명할 수 없고 바이트 해시를 건너뛰게 할 수도
없습니다.

생성된 `RepositoryScanResult`, change set, 소스 다이제스트, World Model 및 GraphSnapshot은
완전한 참조 스캔과 바이트 단위로 동일해야 합니다. 기존 제한, 소스 범위 규칙, symlink 처리,
분류, skip 횟수 및 정식 순서는 바뀌지 않습니다.

## 구성요소 E: 불변 Context 후보 설명자

메모리 내 제한된 캐시는 정확한 World Model 해시, 선별된 지식 다이제스트, 컴파일러 버전 및
예산 프로토콜을 키로 하여 작업 독립적인 설명자를 유지할 수 있습니다. 설명자에는 불변 정식
레코드, 정규화된 용어 집합, 조회 맵, 중요도 및 대략적인 토큰 비용이 포함될 수 있습니다.

모든 컴파일은 계속 작업 용어, 이력 클래스, 관련성, 점수, 전체 후보 순서, 예산 포함 여부, 제외
사유 및 최종 Capsule 해시를 다시 계산합니다. `candidateIds`, `includedIds` 및 전체 제외 레코드는
캐시를 사용하지 않은 컴파일러와 정확히 일치해야 합니다. 시간 확장은 여전히 동일한 제한된 검증
쿼리를 사용하며, 기존의 명시적 옵션이 허용하지 않는 한 검토되지 않은 후보를 소비할 수 없습니다.

캐시 항목은 deep-frozen 상태이며 제한되고 지속되지 않으며, 키 식별자가 하나라도 바뀌면
교체됩니다. 캐시 상태는 Capsule 식별자나 provenance에 절대 들어가지 않습니다.

## 실패 및 fallback 행렬

| 조건 | 필수 동작 |
| --- | --- |
| 선택적 빠른 기능 없음 | 참조 경로를 사용하고 진단을 공개 |
| 읽기 효과 전에 전송 사용 불가 | 문서화된 읽기 fallback 유지 |
| 선택된 네이티브 바이너리 다이제스트 변경 | 참조 fallback 없이 fail-closed 실패 |
| 부분적이거나 잘못된 형식의 배치 | fail-closed 실패 |
| 포인터, 매니페스트, 요청 또는 다이제스트 불일치 | 기존 의미론적 오류로 fail-closed 실패 |
| 읽기 경계가 한 번 변경됨 | 폐기하고 한 번 재시도 |
| 읽기 경계가 다시 변경됨 | fail-closed 실패 |
| 저장소 바이트 다이제스트 변경 | 해당 파일을 파싱하고 정확한 stale/change 상태 보고 |
| 캐시 항목 누락 또는 제거 | 검증된 입력에서 설명자 재구축 |
| 빠른 경로/참조 정식 결과 불일치 | 후보를 비활성화하고 적합성 실패 |

## 구현 단계

1. 운영 프로브와 참조 대비 후보 비교 하네스를 추가합니다.
2. 저장소 최신성 검사와 증분 분석을 바이트 단위로 정확한 단일 패스로 합칩니다. 차등 테스트를
   위해 전체 참조 경로를 유지합니다.
3. 쿼리 전용 exact-child 배치를 선택적 Graph 프로젝션 기능으로 추가하고 현재 전송 경로를
   유지합니다.
4. World Model과 Context 최상위 작업에 `VerifiedReadScope`를 추가합니다.
5. 선택을 변경하지 않고 불변 Context 설명자 캐시를 추가합니다.
6. 기능을 알리기 전에 통합 cold/warm, stale, tamper, crash, cancellation, fallback 및 배포
   테스트를 실행합니다.

각 단계는 독립적으로 되돌릴 수 있습니다. Go 읽기 브리지만 별도의 증거 게이트를 통과했습니다.
이는 저장소 스캔, 정식 검증, 그래프 의미 또는 Context 컴파일이 마이그레이션되었음을 뜻하지
않습니다.

## 승인 증거

병합 게이트에는 다음이 필요합니다.

- 명시적으로 운영적인 진단을 제거한 뒤의 깊은 동등성;
- 참조 경로와 후보 경로에서 동일한 의미 ID와 해시;
- 동일한 후보 순서, 포함, 제외 및 신뢰 경계;
- 동일한 stale, tamper, replay, timeout, cancellation 및 unavailable 오류 분류;
- 새 프로젝트, Canon, checkpoint, review, graph 또는 credential 쓰기 없음;
- exact child 및 하위 프로세스의 정확한 정리;
- 설치된 런타임 표면에 개발 이력이나 검증 fixture 식별자가 없음;
- 대표적인 소형, 중형 및 대형 일반 코퍼스에서 cold-path 비회귀와 반복 가능한 warm-path 개선.

시간 측정은 활성화를 뒷받침하지만 의미론적 정확성을 증명하지는 않습니다. 동등하지만 실질적으로
더 빠르지 않은 후보는 테스트 증거로만 사용할 수 있고 알리지 않습니다. 더 빠르지만 동등하지 않은
후보는 거부합니다.

현재 Windows loopback 승인에서는 정식 응답이 동일한 paired batch 30개를 실행했습니다.
JavaScript exact child의 중앙값은 144.722 ms, Go exact child의 중앙값은 34.624 ms(4.18x)로
측정되었습니다. 이 값은 운영 및 호스트별 값이므로 어떤 의미 식별자에도 들어가지 않으며, 다른
릴리스 호스트에서는 새로 측정해야 합니다. 지속되는 부분은 활성화 규칙입니다. 의미론적 동등성이
통과한 후 네이티브 중앙값이 참조 중앙값의 80 percent 이하여야 합니다.

## 철학적 부합성

이 설계는 원래 Lode 관계를 보존합니다. Lode는 통합과 완료 판단을 소유하고, 사용자는 중대한
방향을 소유하며, 정식 아티팩트는 공급자 세션보다 오래 유지되고, 파생 그래프와 캐시는 대체
가능하며, 제한된 작업자와 어댑터는 권한을 획득할 수 없고, 증거는 판단하는 소비자와 연결된 채로
남아야 합니다. 빠른 경로가 바꾸는 것은 물리적 작업뿐이며, 누가 결정할 수 있는지, 무엇이 참인지,
복구가 어떻게 작동하는지 또는 완료를 무엇으로 보는지는 바꾸지 않습니다.

## 채택 범위와 측정 한계

선택 소유자의 flat shared part, snapshot 소속의 분리, 제한된 private Git batch와 요청 안의 검증 재사용은 구현됐습니다. snapshot 소속은 여전히 전체 그래프 크기에 따라 늘어날 수 있습니다. 이전 합성 저장 성능은 최종 정정 이전의 측정이며 최종 릴리스를 재측정한 결과가 아닙니다. 작거나 반복되는 일부 작업은 더 느렸습니다. P2b와 Rust prototype은 채택하지 않았습니다. 명시적 GC는 coverage index 변경 이전부터 있던 기능입니다.

coverage index는 출력과 callback 순서를 유지하며 의미적 검색을 자체 개선하지 않습니다. [검증 근거](verification-evidence.md#coverage-계산-비교)와 [저장 형식 호환성](snapshot-storage.md)을 참고하세요.
