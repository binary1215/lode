# 기여 안내

[English](CONTRIBUTING.md)

변경을 구체적인 동작이나 반례에 연결하세요. 기존 작업·저작자 표시·소스 식별자와
근거·승인·실행의 구분을 유지하세요. 전면 재작성이나 평상시 작업의 새 게이트를 피하세요.

## 변경 검증

package.json에 명시된 Node.js 24 이상을 사용하세요. 영향을 받는 테스트부터 실행하고,
의미 있는 검사 이름·실패 조건·skip 사유·테스트별 임시 루트를 유지하세요.
공용 helper도 호출마다 새로운 가변 상태를 만들어야 합니다. 실제 하위 프로세스
테스트에는 검증된 supervisor fixture가 필요하며,
[CI workflow](.github/workflows/go-worker-build-release.yml)에 빌드·fixture 준비 절차가 있습니다.
프로세스 소유 검증을 mock으로 대체하지 마세요.

기존 전체 JavaScript 회귀 검사와 문서 검증 명령은 다음과 같습니다.

```text
npm test
npm run verify:docs
```

영향을 받는 계약에 따라 네이티브·배포·런타임 검증을 추가하세요. 통과할 때까지
반복하는 대신 실패 로그를 보존하세요. 검사한 소스 식별자·명령·실제 결과·남은 한계를
기록하세요. 작업 소유 프로세스는 정확한 식별자로 정리하고 공유 프로세스 이름으로
일괄 종료하지 마세요.

## 검증 범위 설명

영어·한국어 문서의 내용을 맞추세요. 소스·단위 검사, 합성 프로토콜 검사,
실제 브라우저 GUI, 실제 provider 동작, 게시·설치·Host 재로드를 구분하세요.
한 종류의 검사나 리뷰 통과가 다른 종류의 성공을 뜻하지 않습니다.

버전 게시에는 별도 승인과 기존 workflow가 필요합니다. 마켓플레이스 스냅샷을
직접 편집하지 마세요. 로컬 개발 목표·비공개 테스트 데이터·자격 증명을 기여에
포함하지 마세요. 민감한 문제를 신고하기 전 [보안 안내](SECURITY.ko.md)를 확인하고,
게시 정책은 [변경 기록](CHANGELOG.ko.md)을 참고하세요.
